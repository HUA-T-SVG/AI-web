# L5 评测报告 · 系统耗时与成本

> 由 `src/core/evaluate/systemEval.test.ts` 产出。复现：
> `pnpm vitest run src/core/evaluate/systemEval.test.ts`（约 36 秒）
>
> 这一层对应设计文档 §5.9.1 的 **L5 系统**（端到端耗时、token 消耗、单次成本），
> 基准是 §2.3 的非功能指标：**5 万行 × 50 列，剖析 ≤ 3 秒；检查全流程 ≤ 30 秒；
> 界面全程不卡顿**。
>
> 测的是 `profileDataset` 与 `runAllChecks` 的**端到端耗时** —— 正是界面上
> 「上传之后那几秒」里跑的东西（目前跑在主线程）。

## 一、耗时（5 万 × 50 列，5 次取中位数）

| 场景 | 中位数 | 最小 | 最大 | 预算 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 剖析 5 万 × 50 | **1464 ms** | 1186 ms | 2148 ms | 3000 ms | ✅ 达标（约 2 倍余量） |
| 全量检查 5 万 × 50 | **10059 ms** | 3422 ms | 11974 ms | 30000 ms | ✅ 达标（约 3 倍余量） |
| 类别归并（500 唯一值 × 3 列，2000 行） | **1266 ms** | 1248 ms | 1290 ms | —— | 单项占全量检查约 13% |

**这些数字必须连着测量条件读 —— 实测过三个批次，差异很大**：

| 批次 | 剖析中位数 | 全量检查中位数 | 当时的机器状态 |
| --- | --- | --- | --- |
| 第一次（无 dev server） | 1108 ms | 3232 ms | 干净 |
| 第二次（**dev server 在跑**） | **4059 ms ❌** | 9750 ms | Turbopack 与 5 万行数据集抢 CPU |
| 第三次（无 dev server，但编辑会话本身有负载） | 1464 ms | 10059 ms | Harness 进程占 CPU |

**所以本表主区用的是最新（也是最保守）的一批**，而上表的意义在于：
**开着 dev server 测性能，会把 1.5 秒的剖析测成 4 秒超预算** —— 那不是实现回归，
是测量污染。这也是坚持报 min/max 的理由：它们比中位数更快暴露「这次测量不可信」
（第二次的抖动是 4576 ms，是第三次的 4.7 倍）。

**数据集刻意是最坏形态**：四分之一的列是逐行唯一的自由文本（每列都要走完整轮
文本归一化）。真实科研数据通常远轻于此。

### 结论一：两项预算都达标

- 剖析约 1.5 秒 / 3 秒预算 —— **不是性能瓶颈**
- 全量检查约 10 秒 / 30 秒预算 —— **不是性能瓶颈**（但已用掉三分之一的余量，
  换更慢的机器时值得复测）

### 结论二：`category-synonyms` 的耗时**与行数无关**，只看唯一值数

单独测 2000 行 × 3 列（每列 500 个唯一值，约 12.5 万对）要 **1266 ms**。
而 5 万行数据集里的分类列只有 4 个唯一值，那部分几乎不耗时 —— 所以这一项在
5 万行数据集上的占比随机器负载波动（第一次测是 36%，第三次是 13%），
**但它的绝对值稳定（1248–1290 ms，抖动仅 42 ms）**。这个反差本身就是结论：
**它只吃唯一值数，不吃行数。**

**这解释了 spec 里那个上限的由来**：`MAX_UNIQUE_VALUES = 500` 不是随便定的，
它把这项检查的成本封在「约 0.4 秒/列」这个量级。若放开到 2000 个唯一值，
代价是平方增长（约 200 万对 → 十秒级），会直接把 30 秒预算吃掉。

### 结论三：Task 8（Worker 化）的定位是**体验**，不是「指标不达标」

按计划的 Step 3：如果全量检查超过 30 秒预算，Task 8 就从「体验优化」升级为
「指标不达标」。**三个批次里最慢的一次也只有约 10 秒，远在预算内** —— 所以：

| 说法 | 是否成立 |
| --- | --- |
| 「Worker 化是为了让检查不超时」 | ❌ 不成立，约 3–10 秒离 30 秒很远 |
| 「Worker 化是为了界面不卡顿」 | ✅ 成立 —— 数秒的同步计算会把主线程冻住，这期间界面无法响应任何点击 |
| 「Worker 化会更快」 | ❌ 不会。搬进 Worker 只是换线程，总耗时基本不变（还要加序列化开销） |

**spec §2.3 的原话是「界面全程不卡顿」** —— 那一条才是 Task 8 的动因。
所以 Task 8 应当**如实**写成体验优化，不要在报告里把它说成「性能不达标所以必须做」。

## 二、token 与成本估算

| 项 | 值 |
| --- | --- |
| 结构摘要字符数 | **8099**（中文/全角 865 字符 · ASCII 7234 字符） |
| 估算输入 token | **≈ 2674** |
| 估算单次分析成本 | **≈ ¥0.0213** |

**先说清这是什么**：这是**估算**，不是实测。真实 token 数要调 API 才知道（属于 Task 5）。
估算口径写在测试文件里：中文按 1 字符 ≈ 1 token、ASCII 按 4 字符 ≈ 1 token
（各家分词器对中文的实际比例在 0.6–1.5 之间波动）。单价硬编码为
DeepSeek 公开定价的量级（输入 ¥2/百万、输出 ¥8/百万），**换模型必须回来改这一处**。

**5 万行 × 50 列的数据，摘要只有 8099 字符。** 这就是「结构摘要」机制的价值：
成本与数据规模**基本脱钩**，单次分析在几分钱量级。若把原始数据传上去，
同一份数据是 MB 级 —— 这也是「数据不出浏览器」在成本侧的收益。

## 三、这一层**没有**覆盖的

| 不覆盖 | 原因 |
| --- | --- |
| 真实 token 数与真实成本 | 要调 API。属于 Task 5（L4）。本报告是估算，界面上写的是「估算」而不是「实测」 |
| 「界面是否真的不卡」 | 那要**在浏览器里量**（长任务、掉帧），不是 Node 里量函数耗时能回答的。Task 8 做完之后应当在真浏览器里测一次 |
| 端侧 embedding 的耗时 | 模型首次下载约 25 MB，那由 `embedding-validation.md` 与 E2E 覆盖；本报告只测确定性检查 |
| 解析（CSV/Excel）的耗时 | 那是 `parser/` 的事，已由 `workerClient` 与 E2E 覆盖 |
| 移动端 / 低端机 | 本报告跑在开发机。§2.3 的预算对低端机是否成立**没有验证** |

## 四、维护

改动以下任一项之后要重跑本表：

- `profileDataset` / `runAllChecks` 的实现或检查项增减
- `MAX_UNIQUE_VALUES`（它直接决定类别归并的成本）
- 换了机器（性能结论与机器强相关，本表的数字**只在同类机器上可比**）

```bash
pnpm vitest run src/core/evaluate/systemEval.test.ts
```
