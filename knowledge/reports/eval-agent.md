## 二、四条重要结论（前三条的「问题」都已部分改善，最后一条是剩余成本）

### 结论一：提示词层的收敛判据**有效，但只解决一半**

补上判据（计划覆盖完 / 提交满 8 条 / 连续两次无新线索 → 立刻总结并停止）之后：

- 截断从 **6/12 降到 3/12**（连续三次复测都是 3/12）；`defects` 从「3/3 撞满」
  变成 **0/3**，三次都在第 13 轮自然收尾并给出总结；
- `defects` 的提交条数从 4/7/8 变成 **7/8/8**：不再「早停漏报」，也不再「反复看列」；
- 越界请求三次都先明确拒绝（见结论四）。

但它**没有降低平均轮次**（7.17 → 7.58），原因是一条硬约束：

> **`submit_issue` 一次只能提交一条**（刻意的载荷设计，见
> `agent/shared/toolSchemas.ts`）。提交 8 条问题就要 8 轮，再加上计划、执行、
> 查规则、看列，8 条满报的路径天然要 13–15 轮 —— 提示词能决定「何时停」，
> 决定不了「一条一轮」的成本。`defects` 的评测窗口因此从 12 调到 14
> （`agent-queries.json` 里写了这次调整的算术）。

### 结论二：「该不该继续查」不是提示词能管住的

`off-topic` 问的是统计建模（产品明确不做），三次回复都先拒绝了；但三次都在拒绝
之后继续查质量、提交 2–7 条、**全部撞满 6 轮窗口**。这属于「意图层的取舍」，靠提示词
没有稳定效果 —— 要么给它更长的窗口，要么在产品层判断「越界请求只做轻量检查」。

### 结论三：同一条查询的产出**比之前稳定，但仍不是分布**

`defects` 是 7/8/8（之前 4/7/8）；`off-topic` 是 2/7/2（之前 4/1/2）；
`rule-lookup` 是 7/0/0（之前 0/0/5）。方差仍然大，而**每条查询只有 3 次**，
只能说「不稳定/有改善」，不能给方差或置信区间。

### 结论四：「越界请求」的拒绝仍然是**合格的**

`off-topic` 问「算相关系数矩阵并做多元回归」，而产品明确不做统计建模
（设计文档 §2.4）。三次运行的回复都明确说了做不到，并说明原因：

> 「相关系数矩阵和多元回归我无法直接给出数值结果……这里的工具只能做数据质量检查……
> 这份数据目前不具备做回归的条件 —— 没有明确的结果变量」

**它没有硬编一段回归结果**，而是把话题拉回数据质量。这是这一层最正面的一条。

## 三、结构化检查发现的一个真问题

计划里出现了**编造的检查项**：`checkId = "describe-剂量"`。

这是**好消息**：生产的执行器（`toolExecutors.ts`）把它拦下了，所以它没进到用户面前。
但它说明**模型会编造 `checkId`** —— 而工具契约里写了「取值必须是可用检查项之一」。
这一条正是「工具校验属于被测对象」的实证：若评测脚本另写一份不带校验的执行器，
这个编造值会被静默接受，评测就成了自欺。

（注：该条的 `targetColumns` 引用了真实存在的列，所以问题只在 `checkId` 上。）

## 四、口径的限制（必须写明，不许含糊）

| 指标 | 局限 |
| --- | --- |
| 工具调用正确率 | 只判「调了没有」。一个把 `run_checks` 参数填错的运行也算通过 —— 所以它必须与**工具成功率**一起读 |
| **计划合理性** | **无法自动评**。本报告只做结构化检查（`checkId` 合法、列名存在、≤8 条），那是「格式与引用成立」，**不是「计划合理」**。真要评得人工看，属于人工评估 |
| 失败恢复率 | 本轮 3/3 全部恢复。但「恢复」的定义是「失败后仍继续推进」，不是「最终产出了正确结论」 |
| **样本量** | 每条查询只跑 **3 次**。3 次不足以谈分布，上面的数字只能说「这次是这样」，**不能给出方差或置信区间**；本轮与上一轮的差异也可能有一部分是模型自身的随机性 |
| 端到端耗时 | 12 次对话共约 4 分钟，即**每次约 20 秒**。但这取决于模型服务的响应速度，不是产品自身的性能（产品自身的耗时见 `eval-system.md`） |

## 五、token 与成本：**现在测得到了（T2）**

服务端在流的 `finish` 事件里把 `totalUsage` 随消息元数据带回（`route.ts` 的
`messageMetadata`）。本轮 12 次对话、**91 个请求全部上报了 usage**：

| 项 | 值 |
| --- | --- |
| 输入 token（12 次合计） | **684,554** |
| 输出 token（12 次合计） | **27,247** |
| 合计 | **711,801** |
| **单次分析成本（估算）** | **≈ ¥0.13**（输入 ¥2/百万 + 输出 ¥8/百万，单价硬编码、换模型要改） |

**这个数值得单独说一句：它比早期估算的 ¥0.02 高了约 6 倍。** 早期估算是按
「结构摘要 2674 输入 token」算的，**忽略了多轮工具循环**：平均 7.6 轮、每轮都把
累积的会话历史重新发一遍，输入 token 随轮次近似线性增长。所以：

> 「数据不出浏览器、发出去的只是摘要」这句话在隐私上成立，但**不能推出「成本很低」** ——
> 真正决定成本的是**轮次**。T11（减少轮次）同时也是成本优化，不只是体验问题。

成本仍是**估算**而非账单：usage 是真的，单价是硬编码的公开量级。

## 六、这次评测**没有**覆盖的

| 不覆盖 | 原因 |
| --- | --- |
| 成本是「估算」而非账单 | usage 是真的；单价按公开量级硬编码，换模型必须回来改（见 §五） |
| 工具结果的质量（问题报得对不对） | 那是 **L1** 的事（`eval-l1.md`）。这一层只评「工具有没有被正确调用、流程有没有跑完」 |
| 多轮追问（用户接着改主意） | 每条查询都是单轮问答，没有测「用户拒绝了一条结论之后再问」 |
| 规则检索这条路的效果 | `query_rules` 在本轮**成功**了（补了 fetch 补丁），但检索质量是 **L3** 的事（`eval-retrieval.md`） |
| 并发与限流 | 串行跑 12 次对话，没有测并发下的表现 |

## 七、跑法与维护

```bash
# 1) 先起服务（评测脚本会 POST /api/agent）
pnpm dev
# 2) 另开一个终端
pnpm eval:agent
```

- 默认每条查询跑 3 次；改次数：`$env:AGENT_EVAL_RUNS=1; pnpm eval:agent`
- 换接口地址：`$env:AGENT_ENDPOINT='http://localhost:3000/api/agent'`
- **不进日常门禁**：`pnpm test` 会跳过本文件（它靠 `RUN_AGENT_EVAL` 环境变量开启，
  而那条变量由 `eval:agent` 脚本设置）

**下一步该做什么**（按本报告的结论）：

1. ~~在系统指令里写明收敛判据~~ —— **已做（2026-10-20）**，效果见 §一/§二；
2. **重新权衡 `submit_issue` 的载荷设计**（登记为 T11）：要么允许一次提交 2–3 条
   （真模型实测过「整份报告一次提交」会导致工具输入流不完，少量批量未测），
   要么在浏览器侧「提交满 8 条后不再自动续轮」。**这两条都会改产品行为，属所有者决策**；
3. 越界请求的轻量处理（意图层）：产品层识别「统计建模类请求」并限制检查轮次，
   而不是靠提示词劝。

在此之前，「平均轮次」仍**不适合**单独写进技术文档当成绩 —— 它量的是「模型想查多久」，
而「被截断」与「提交条数」才是能说明收敛质量的指标。
