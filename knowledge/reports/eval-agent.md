## 二、五条重要结论

### 结论一：提示词层的收敛判据**有效，但仍被「一条一轮」的载荷设计卡住**

- 截断保持 **3/12**，且 `off-topic` 独吞全部 3 次截断；`defects` 三次都在第 12–13 轮
  自然收尾并给出总结；
- `defects` 提交 **7 / 8 / 8**：不再「早停漏报」，也没有再出现 8 条以上的不稳定；
- 平均轮次从 7.58 降到 **6.67**，但这**不是判据变聪明了**：一次是在 30 步上限下
  模型自己少绕了圈，另一次是样本随机性（3 次/查询，谈不了分布）。
  真正的结构成本仍在：
  > **`submit_issue` 一次只能提交一条**。提交 8 条就要 8 轮，加计划/执行/查规则/看列，
  > 满报路径天然 12–15 轮 —— 提示词能决定「何时停」，决定不了「一条一轮」的成本。
  这就是 T11（批量提交 / 满 8 条自动停止）仍然值得做的原因，属所有者决策。

### 结论二：「该不该继续查」不是提示词能管住的（未改善）

`off-topic` 问统计建模（产品明确不做），三次回复都先拒绝了，但三次都在拒绝之后
继续查质量、提交 2–3 条、**全部撞满 6 轮窗口**。要靠提示词稳定压住它并不现实 ——
要么给它更长窗口，要么在产品层做意图判断（越界请求只做轻量检查）。

### 结论三：工具成功率 100% **不能当成稳定结论**

本轮 86 次工具调用全部返回 ok，但同日更早一次运行（同一配置、修正口径前）出现过：
- 8 个编造的 `checkId`（`dup-col` / `dup-row` / `age-range` / `height-range` /
  `dose-unit` / `edu-synonym` / `mixed-type` / `group-missing`）；
- 编造学科 `药学` 去检索规则库。
两次都被**生产执行器**当场拦下并回填可读错误，模型随后自纠。
2026-10-20 那轮也出现过 `describe-剂量`。**所以「模型会编造」是间歇性的，
校验不是可选项；一轮干净不代表它不会编造。**

### 结论四：「越界请求」的拒绝仍然是**合格的**

`off-topic` 三次回复都明确说了做不到，并把话题拉回数据质量：

> 「相关系数矩阵和多元回归我无法直接给出数值结果……这里的工具只能做数据质量检查……
> 这份数据目前不具备做回归的条件 —— 没有明确的结果变量」

**它没有硬编一段回归结果**。这是这一层最正面的一条；问题只在于拒绝之后还会继续查
（见结论二）。

### 结论五：**契约与实现的一处落差已修复**（2026-11-01）

`submit_issue` 的工具描述与系统指令都写「最多 8 条」，但此前运行时并未强制
（只校验 checkId 与列名），同日更早一次运行中 `defects` 提交过 **9 条**。
T11 拍板选低风险方案：**运行时硬上限** —— 第 9 条由执行器拒绝并回填可读错误
（「已提交 8 条（上限），请直接总结」）；界面取审阅列表实时条数、L4 评测共用同一
执行器。**批量提交不做**：它能省约 20–35% 成本，但小批量载荷在真模型上未验证，
赛前不动核心链路。本轮 7/8/8 未触发上限。

## 三、口径的限制（必须写明，不许含糊）

| 指标 | 局限 |
| --- | --- |
| 工具调用正确率 | 只判「调了没有」。参数填错的运行也算通过 —— 必须与**工具成功率**一起读 |
| **计划合理性** | **无法自动评**。只做结构化检查（`checkId` 合法、列名存在、≤8 条），那是「格式与引用成立」，**不是「计划合理」**。要评得人工看 |
| 失败恢复率 | 本轮没有失败，因此是 **n/a**；不能把「没发生」写成「100% 恢复」 |
| 追问 | L4 没有真实用户，`ask_clarification` 一律模拟为「跳过」；**真实回答路径由追问 E2E 与线上冒烟覆盖**，本报告不评它 |
| **样本量** | 每条查询只跑 **3 次**，不能给方差或置信区间；跨轮次比较只能看方向 |
| 配置变化 | 本轮 `MAX_STEPS=30`，与 10-20 的 20 不同；跨配置比较不能当作「同一实验的重复」 |
| 端到端耗时 | 12 次对话约 3 分钟，即每次约 20 秒；这取决于模型服务，不是产品自身性能（见 `eval-system.md`） |

## 四、token 与成本

| 项 | 值 |
| --- | --- |
| 输入 token（12 次合计） | **650,532** |
| 输出 token（12 次合计） | **22,800** |
| 合计 | **673,332** |
| 上报覆盖 | **80/80 轮**都带了 usage |
| **单次分析成本（估算）** | **≈ ¥0.1236**（输入 ¥2/百万 + 输出 ¥8/百万，单价硬编码） |
| 12 次合计 | ≈ ¥1.48 |

**「只发摘要」在隐私上成立，但推不出「成本低」**：真正决定成本的是**轮次**
（每轮都把累积会话历史重新发一遍）。本轮平均 6.67 轮、单次约 ¥0.12；
T11（减少轮次）同时也是成本优化。成本仍是**估算**而非平台账单。

## 五、这次评测**没有**覆盖的

| 不覆盖 | 原因 |
| --- | --- |
| 成本是「估算」而非账单 | usage 是真的；单价按公开量级硬编码，换模型必须回来改 |
| 工具结果的质量（问题报得对不对） | 那是 **L1** 的事（`eval-l1.md`） |
| 追问的真实回答路径 | L4 模拟为「跳过」；真实作答由 E2E 与线上冒烟覆盖 |
| 规则检索这条路的效果 | `query_rules` 被调用过；检索质量是 **L3**（`eval-retrieval.md`） |
| 并发与限流 | 串行跑 12 次对话，没有测并发 |
| 「最多 8 条」的运行时强制 | 已实现（2026-11-01，见结论五）：第 9 条返回可读错误并引导收尾 |

## 六、跑法与维护

```bash
# 1) 先起服务（评测脚本会 POST /api/agent）
pnpm dev
# 2) 另开一个终端
pnpm eval:agent
```

- 默认每条查询跑 3 次；改次数：`$env:AGENT_EVAL_RUNS=1; pnpm eval:agent`
- 换接口地址：`$env:AGENT_ENDPOINT='http://localhost:3000/api/agent'`
- **不进日常门禁**：`pnpm test` 会跳过本文件（靠 `RUN_AGENT_EVAL` 开启，由 `eval:agent` 脚本设置）
- **口径变更史（跨轮比较必看）**：2026-10-20 补收敛判据；2026-10-28 `MAX_STEPS` 20→30；
  2026-11-01 L4 把 `ask_clarification` 改为「模拟跳过」——修正前的数字会把追问算成工具失败。

**下一步该做什么**（按本报告的结论）：

1. ~~在系统指令里写明收敛判据~~ —— 已做（2026-10-20）；
