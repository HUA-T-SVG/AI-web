## 二、三条重要结论（前两条是问题）

### 结论一：Agent 跑得起来，但**一半的运行没跑完**

`6/12` 被轮次上限截断，其中 **`defects` 三次全部撞到 12 轮上限**；`off-topic` 也
三次全撞。

**第一次跑时这个数字被掩盖了**：当时上限是 8，三次都恰好 8 轮，看起来像「稳定完成」。
是加了 `hitRoundLimit` 标记之后才看出那是**每次都在上限处被截断**。
这件事本身值得记：**指标里必须区分「自然结束」与「被截断」** —— 只看平均轮次，
截断会被读成一致性。

原因不神秘，是这套工作流的固有成本：`plan_checks` 1 轮 → `run_checks` 1 轮 →
中间查规则、看列细节各若干轮 → 而 **`submit_issue` 一次只能提交一条**（刻意的载荷
设计，见 `agent/shared/toolSchemas.ts`），提交 8 条问题就要 8 轮。
`defects` 那次在 12 轮里竟然调了 **7 次 `describe_column`** —— 它在反复看列细节，
而不是尽快给结论。

### 结论二：同一条查询的产出**不稳定**

`defects` 三次分别提交 **4 / 7 / 8** 条问题；`off-topic` 三次提交 **4 / 1 / 2** 条。
`rule-lookup` 更极端：前两次 2 轮就答完、0 条问题，第三次却跑成 9 轮并提交 5 条。

这不是「随机波动」那么简单 —— 它说明**没有收敛判据**。模型不知道「查得够了」，
于是要么早停（`rule-lookup` 前两次），要么一直查到被上限打断（`defects`）。

### 结论三：「越界请求」的拒绝是**合格的**

`off-topic` 问「算相关系数矩阵并做多元回归」，而产品明确不做统计建模
（设计文档 §2.4）。三次运行的回复都明确说了做不到，并说明原因：

> 「相关系数矩阵和多元回归我无法直接给出数值结果……这里的工具只能做数据质量检查……
> 这份数据目前不具备做回归的条件 —— 没有明确的结果变量」

**它没有硬编一段回归结果**，而是把话题拉回数据质量。这是这一层最正面的一条。

## 三、结构化检查发现的一个真问题

计划里出现了**编造的检查项**：`checkId = "describe-剂量"`。

这是**好消息**：生产的执行器（`toolExecutors.ts`）把它拦下了，所以它没进到用户面前。
但它说明**模型会编造 `checkId`** —— 而工具契约里写了「取值必须是可用检查项之一」。
这一条正是「工具校验属于被测对象」的实证：若评测脚本另写一份不带校验的执行器，
这个编造值会被静默接受，评测就成了自欺。

（注：该条的 `targetColumns` 引用了真实存在的列，所以问题只在 `checkId` 上。）

## 四、口径的限制（必须写明，不许含糊）

| 指标 | 局限 |
| --- | --- |
| 工具调用正确率 | 只判「调了没有」。一个把 `run_checks` 参数填错的运行也算通过 —— 所以它必须与**工具成功率**一起读 |
| **计划合理性** | **无法自动评**。本报告只做结构化检查（`checkId` 合法、列名存在、≤8 条），那是「格式与引用成立」，**不是「计划合理」**。真要评得人工看，属于人工评估 |
| 失败恢复率 | 本轮 5/5 全部恢复。但「恢复」的定义是「失败后仍继续推进」，不是「最终产出了正确结论」 |
| **样本量** | 每条查询只跑 **3 次**。3 次不足以谈分布，上面的 [4,7,8] 只能说「不稳定」，**不能给出方差或置信区间** |
| 端到端耗时 | 12 次对话共约 4 分钟，即**每次约 20 秒**。但这取决于模型服务的响应速度，不是产品自身的性能（产品自身的耗时见 `eval-system.md`） |

## 五、token 与成本：**测不到**

本轮**没有拿到真实 token 用量**。原因：`POST /api/agent` 的 SSE 流里，
`finish` 块只带 `finishReason`，**不带 usage**（真跑时验证过）。要拿到得改
`/api/agent` 把 `streamText` 的 usage 透出来 —— 那是产品代码的改动，为了评测而改
产品的出站协议不划算，所以这里如实记为「未测」。

成本只能按调用次数估：12 次对话约 **117 次工具调用 + 60 余次模型请求**，
按 `eval-system.md` 的估算（单次输入约 ¥0.02 量级）**总费用在 ¥1–2**。

## 六、这次评测**没有**覆盖的

| 不覆盖 | 原因 |
| --- | --- |
| 真实 token 与成本 | 见上，SSE 流不给 usage |
| 工具结果的质量（问题报得对不对） | 那是 **L1** 的事（`eval-l1.md`）。这一层只评「工具有没有被正确调用、流程有没有跑完」 |
| 多轮追问（用户接着改主意） | 每条查询都是单轮问答，没有测「用户拒绝了一条结论之后再问」 |
| 规则检索这条路的效果 | `query_rules` 在本轮**成功**了（补了 fetch 补丁），但检索质量是 **L3** 的事（`eval-retrieval.md`） |
| 并发与限流 | 串行跑 12 次对话，没有测并发下的表现 |

## 七、跑法与维护

```bash
# 1) 先起服务（评测脚本会 POST /api/agent）
pnpm dev
# 2) 另开一个终端
pnpm eval:agent
```

- 默认每条查询跑 3 次；改次数：`$env:AGENT_EVAL_RUNS=1; pnpm eval:agent`
- 换接口地址：`$env:AGENT_ENDPOINT='http://localhost:3000/api/agent'`
- **不进日常门禁**：`pnpm test` 会跳过本文件（它靠 `RUN_AGENT_EVAL` 环境变量开启，
  而那条变量由 `eval:agent` 脚本设置）

**下一步该做什么**（按本报告的结论）：给 Agent 一个**收敛判据** —— 要么在系统
指令里写明「查够 N 项就该收尾」，要么给 `submit_issue` 一个批量入口（但那与
「一次一条」的载荷设计冲突，需要重新权衡）。在此之前，「平均轮次」与「提交条数」
这两个指标都**不适合**写进技术文档当成绩 —— 它们现在量的是「模型想查多久」，
不是「产品有多能干」。
