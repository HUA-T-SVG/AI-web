# 端到端时长与卡顿实测（2026-11-11）

> 由 `scripts/measure-e2e-timing.mjs` 产出（`pnpm measure:e2e`）。复现需要：
> `pnpm build && pnpm start` 在 3000 端口运行、`.env.local` 配真实模型；
> **每次完整分析会产生模型费用**（约 ¥0.12/次）。
>
> 原始数据：`e2e-timing.raw.json`（正常 3 次）· `e2e-timing-cpu4.raw.json`（4× CPU 降速 1 次）·
> `e2e-timing-settle.raw.json`（归属对照 1 次）。
>
> 这一层补的是此前登记在技术文档 §8.2 的缺口：**语义归并 + 多轮 LLM 的端到端时长、
> 以及浏览器里的长任务/掉帧从未整段量过**。此前只有确定性检查的 Node 侧耗时（3.45 s）。

## 一、测了什么

一次完整的用户路径，全部在**生产构建**（`next start`）上跑：

1. `/import` 上传 `knowledge/eval/dataset/messy-eval.csv`（1002 行 × 12 列）→ 解析 + 画像；
2. 进入 `/analysis`，提问「这份数据有什么质量问题？请全面检查，逐条给出结论。」；
3. 等计划出现 → 点「按此计划执行」→ 模型多轮工具调用（真实模型）→ 收尾总结；
4. 浏览器内用 `PerformanceObserver` 收 `longtask`（>50 ms 的主线程任务），
   用 `requestAnimationFrame` 采样帧间隔，统计掉帧（间隔 >50 ms）与最长帧间隔。

环境：本机、Chromium（headless）、1440×1000、生产构建、真实模型（`LLM_MODEL` 配置在 `.env.local`）。
计时口径：「计划」= 点「开始分析」→ 计划按钮可点；「执行」= 点「按此计划执行」→ 最后一个
`/api/agent` 请求结束；「首段反馈」= 点「开始分析」→ 界面上出现第一段助手内容。

## 二、结果

### 2.1 正常流程（3 次）

| 阶段 | 中位数 | 范围 |
| --- | --- | --- |
| 导入（解析 + 画像） | **0.83 s** | 0.77–0.88 s |
| 首段反馈 | **1.67 s** | 1.58–4.06 s |
| 计划阶段（等模型给出计划） | **4.06 s** | 3.87–8.03 s |
| 执行阶段（按计划跑完 + 总结） | **1.93 s** | 1.63–2.48 s |
| **端到端（点击开始 → 最后一条结论）** | **9.91 s** | 6.06–10.55 s |
| 请求轮数 | 4 轮 | 4 轮 |
| 主线程长任务（>50 ms） | **2 个 / 合计 3.99 s** | 2–4 个 / 2.47–3.99 s |
| 最长单个长任务 | **3.78 s** | 2.34–3.93 s |
| 掉帧（帧间隔 >50 ms） | 4 帧 | 2–4 帧 |
| 最长帧间隔 | 3.78 s | 2.33–3.92 s |

### 2.2 4× CPU 降速（1 次，模拟弱设备）

| 指标 | 值 |
| --- | --- |
| 端到端 | **20.04 s**（计划 18.30 s） |
| 主线程长任务 | **9 个 / 合计 7.11 s**，最长 **6.19 s** |
| 掉帧 | 14 帧，最长帧间隔 6.18 s |

降速放大了同一处卡顿：模型加载与渲染在慢 CPU 上更久。

### 2.3 归属对照：先等 9 秒再开始（1 次）

| 指标 | 值 |
| --- | --- |
| 端到端 | 19.75 s（这一次模型本身慢：计划阶段 17.84 s） |
| 主线程长任务 | **4 个 / 合计 288 ms**，最长 **88 ms** |
| 掉帧 | 2 帧，最长帧间隔 **66.7 ms** |

**结论归属**：多秒级长任务不是分析计算造成的（检查/画像在 Worker 里、模型请求是异步等待），
而是**导入完成后自动跑的语义归并首次加载 25 MB 模型**；用户紧接着点「开始分析」时两者重叠。
先让语义归并跑完，长任务从「最大 3.9 s」降到「最大 88 ms」。

## 三、结论（答辩口径）

1. **端到端时长**：真实模型下中位约 **9.9 s**（6.1–10.6 s），其中计划阶段 4.1 s、执行 1.9 s、
   导入 0.8 s。远低于「检查全流程 ≤30 s」的预算，但**时间主要花在等模型**，
   同配置再跑一次出现过 19.8 s（计划 17.8 s）——provider 延迟波动大，不能承诺固定上限。
2. **界面卡不卡**：**仍未达到「全程不卡顿」**。快速「导入→立即分析」时，首次语义模型加载
   与开始分析重叠，主线程出现 2–4 个长任务（最大 2.3–3.9 s）；4× CPU 下降速到 6.2 s。
   等它加载完则最长长任务 88 ms。
3. **已做的抑制**：移除全局后台预取（原 `EmbeddingPrefetch` 挂载 3 s 后加载模型，现改为
   `ClientBoot` 只保留 hydrated 信号），避免在分析与首屏阶段再主动触发 25 MB 加载。
   语义归并仍会在导入后按需触发，因此「快速开始」仍可能重叠 —— 这是剩余限制。
4. **彻底修复方向（未做，已登记 §8.3）**：把 embedding 加载与推理移进 Web Worker，
   让主线程只收向量结果。工作量与风险都高于本次赛前窗口，故只做测量与预取抑制。

## 四、口径限制

- 只有 3 次正常 + 1 次降速 + 1 次对照；模型服务延迟波动大，**不是分布**，不给置信区间；
- headless Chromium、本机网络；未覆盖 Safari/Firefox 与真机移动端；
- 掉帧用 rAF 间隔近似，长任务用 `longtask` entry（>50 ms），均为主线程指标；
- 「执行阶段」不含用户看视频/思考时间（脚本自动点计划）；
- 4× CPU 降速只跑 1 次，仅作方向性证据。
