# L3 评测报告 · RAG 检索质量

> 由 `src/knowledge/retrievalEval.test.ts` 产出（跑的是**生产检索实现**，不是抄本）。
> 复现：`pnpm vitest run src/knowledge/retrievalEval.test.ts`
>
> 查询集：`knowledge/eval/retrieval-queries.json`（21 条 = 8 条学科专属 + 11 条通用 + 2 条边界）
> 索引：`knowledge/index/rules.json`（178 条）→ 同步到 `public/knowledge/`
>
> 这一层对应设计文档 §5.9.1 的 **L3 RAG**，也是评分点里唯一有明文要求的一层
> （「RAG 技术应用 6%」：**建立检索评测集验证有效性**）。

## 一、结果

| 指标 | 值 | 达标线 | 是否达标 |
| --- | --- | --- | --- |
| **Hit@1** | **78.9%**（15/19） | —— | —— |
| **Hit@5** | **94.7%**（18/19） | ≥ 90% | ✅ |
| **MRR** | **0.8684** | ≥ 0.7 | ✅ |
| 边界查询误召回 | 0 条（1 条查询）/ 2 条（另 1 条） | 见下 | ⚠️ 见下 |

达标线是本项目定的（spec 没给检索的达标线），理由写在查询集 JSON 里：
注入 Prompt 的是 Top-5，所以只要答案落在前五条模型就能用到；MRR 保证它不是永远排第五。

**这组数字比 113 条索引时低，必须如实说。** 113 条时是 Hit@1 94.7% / Hit@5 100% / MRR 0.9737；
换成 178 条多学科扩展版后降到上表。原因不是检索代码改了，而是：
① 新库比旧库多 65 条、且原 110 条正文被重写过，同义/近义条目的字面重叠变多，排序竞争更激烈；
② 当前后端是离线字符 2-gram 哈希，只按字面重叠打分，区分不了「都在讲日期/编码」的相近条目。
**没有为了把数字拉回来去改查询集** —— 查询集是评测基准，改它就等于改考卷。

**4 条没排到第 1 的查询**（不是测试写错，逐条说明）：

| 查询 | 实际 | 说明 |
| --- | --- | --- |
| `学期 2023-2024-1 …` | **未进前 5** | 期望 `ds-term-year-encoding`。字面被 `general-date-ambiguous` 等日期类条目挤占；这是本轮最直接暴露的后端弱点 |
| `单位 mg g 剂量 500 1000` | #2（期望 `general-unit-mixed`） | 第 1 名 `general-case-unit-conversion-direction` 讲的是单位换算方向，与查询字面同样高度重合 |
| `学号 001 002 003 前导零` | #2（期望 `general-case-leading-zero-lost`） | 第 1 名 `general-case-join-key-type-mismatch` 同样大量提及学号/编号 |
| `全角 空格 隐形字符 本科在读` | #2（期望 `general-fullwidth`） | 第 1 名 `general-enrolled-status`：「本科在读」四个字本身就是它的强信号，而查询想表达的是全角/隐形字符问题 |

这四条都**保留原表述**，不改成「必中第 1」——评测的价值在于它还能报出坏消息。

## 二、分层的表现

| 类别 | 条数 | 表现 |
| --- | --- | --- |
| **学科专属**（8 条，期望命中 `ds-*`） | 8 | 7 条 #1（绩点、成绩特殊标记、学分、在校生数、学籍状态、课程号改版、实验量程与批次）；「学年学期编码」一条未进前 5 |
| **通用**（11 条，期望命中 `general-*`） | 11 | 8 条 #1、3 条 #2 |
| **边界**（2 条） | 2 | 见下 |

**学科专属曾经结构上不可达**：Plan 3 时 `subject` 是死参数，不传时候选集只含「通用」。
§8.10 改成「学科只加权、不排除」之后它们才第一次真正能被检索到。
这份报告里学科查询 7/8 排到第 1，仍是那处修改仍然有效的证据。

## 三、边界查询：这个后端的固有弱点（要如实记）

| 查询 | 实际召回 | 说明 |
| --- | --- | --- |
| `菜谱 火候 调味 翻炒 腌制` | **0 条** | 期望的样子 |
| `量子纠缠 波函数 薛定谔方程 自旋` | **2 条**（`general-case-vlookup-approximate`、`general-case-filter-then-stats`） | **不该有，但有** |

第二条不是测试写错了，而是**字符 2-gram 后端的本质**：它只按字面重叠打分，
两个中文字如果有共同的 2-gram 就会给分，**完全不理解「量子纠缠」与「数据质量」是两回事**。

测试里有一条断言专门守这件事：这些误召回**不得**被伪装成「语义相近」
（`reason` 里不能出现那四个字）。理由与 Plan 3 一致 —— **错误注入比不注入更坏**。

**这条用例的价值就是把后端弱点量出来**，它是「必须换 bge 后端」的证据之一，
与 `embedding-validation.md` 里 Hit@1 连续多批下滑的记录互为印证。

## 四、与构建脚本的自召回对照（**两者都乐观，方向不同**）

| 来源 | Hit@1 | 性质 |
| --- | --- | --- |
| `build-index.py` 的自召回（178 条） | 0.8427（Hit@5 0.9663 / MRR 0.8979） | 用**规则自己的正例**造查询 → 与目标条目共享正例词汇，天然偏乐观 |
| **本报告**（手写评测集，178 条） | **0.789** | 查询表述**取自规则描述的关键词** → 同样偏乐观 |

**这不是说检索实测有 78.9% 的命中率。** 两件事都必须写明：

1. **查询是手写的，不是 Agent 真实会发出来的**。真实链路里 `query_rules` 的 query
   由列名 + 取值分布拼成（如「学历 硕士 研究生 本科」），比本报告的查询更粗、更短。
   所以本报告的高分里有一部分是「我知道答案，所以按答案的关键词提问」。
2. **真正公平的做法**是拿 Agent 真实发出的 query 做回归集，那属于 L4（Task 5）。
   本报告的定位是**检索管线的冒烟评测**，不是端到端效果。

写这条对照是刻意的：Plan 1–3 里反复出现过「好看的指标其实没有效力」，
这一层的风险恰好相反 —— **指标好看，但采样偏向了答案**。
这一轮数字降下来，反而说明这份评测是能报坏消息的。

## 五、这一层**没有**覆盖的

| 不覆盖 | 原因 |
| --- | --- |
| 稠密路（语义检索）的质量 | 当前索引后端是 `char-ngram-hash`，`queryModel` 配对检查会**关掉稠密路**。所以本报告测的是纯稀疏路 —— 测试里的 embedder 一被调用就抛错，这条断言守着「不该碰模型」 |
| 检索结果的**生成**质量（规则正文有没有帮到模型） | 那属于 L4。这一层只评「该召回的有没有召回到、排第几」 |
| 学科过滤（`subject`）的效果 | 已由 `retrieve.test.ts` 的对照用例覆盖（传/不传 subject 的排序差异） |
| 新增的 5 个学科包（心理学/教育学/公共卫生/社会学/经济学） | 查询集只有 8 条数据科学专属查询；新学科包各自 5 条，**没有专属评测查询**，属于下一轮要补的评测覆盖 |
| 跨学科泛化 | 索引有 7 个学科取值（共 52 条学科专属），但评测查询只覆盖了其中 1 个学科 |

## 六、跑法与维护

```bash
pnpm vitest run src/knowledge/retrievalEval.test.ts
```

**改动以下任一项之后必须重跑本表**：

- 索引重建（`build-index.py`）· 换 embedding 后端（`--embedder bge`）
- `retrieveRules` 的排序逻辑（BM25 参数、RRF 的 k、列名/学科加权）
- 规则条目的增删（`expected` 里的 id 失效时测试会立刻报出来：查询集里有一条断言核对所有期望 id 都真实存在）

换 bge 后端之后，**边界查询的误召回数应当显著下降、相邻条目的排序也应当更稳** ——
那也是换后端是否成功的判据之一。
