# 有无 RAG 配对评测 · 生成判断、暂缓和引用

这份评测补上原 [L3 检索评测](eval-retrieval.md) 没测的部分：进入候选的资料，能否帮助同一个大模型做出正确的数据口径判断；没有合适资料时，它会不会仍硬套规则。现有检索评测的 Hit@5 不等于这里的模型判断准确率。

## 如何运行

1. 在项目根目录配置 `.env.local`（沿用 `.env.example` 的 `LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL`）。不需要启动网页。
2. 执行 `npm run eval:rag`。默认按 `rag-comparison-cases.json` 的 14 个合成案例，发送两组请求，共 28 次独立请求。命令会调用已配置的模型服务并使用其配额。
3. 查看控制台给出的 `.tmp/rag-comparison/<UTC 时间>/summary.md` 与 `raw.json`。原始文件包含各组输出、判断选项、候选与引用 ID、耗时及模型返回的 token 用量；供应商错误只记分类或状态码，不记录凭据或原始报错。用于公开复核的 `observations.json` 去除了模型自由文本。

可用 `RAG_COMPARISON_REPEATS=2` 重复，每个案例是成对重复；也可通过逗号分隔的 `RAG_COMPARISON_CASES` 只跑指定案例。子集明确标为冒烟，不能当全量结果。只验证评测程序、不发模型请求：`npm test -- src/agent/evaluate/ragComparison.test.ts`。

PowerShell 中复跑本报告的两次配对：`$env:RAG_COMPARISON_REPEATS='2'; npm run eval:rag`。

## 对照口径

| 条件 | 无 RAG | 有 RAG |
| --- | --- | --- |
| 模型、输出约定、温度、候选选项、题目 | 两组相同，温度 0 | 两组相同，温度 0 |
| 候选规则 | 空数组 | 同一份生产索引，调用 `retrieveRules`，使用字段、学科与生产默认 Top-K，按实际出站白名单给模型 |
| 请求顺序 | 先后交替，重复时反转 | 先后交替，重复时反转 |

- 案例提前标注预期选项、是否应暂缓或追问、允许引用的规则 ID。标注及检索用查询都不发给模型。案例有明确口径、缺失码正反例、同名歧义、冲突与无适用规则。
- 决策计分要求**选项与是否暂缓均正确**。某个引用要计为有效，必须同时出现在该次检索给模型的候选和人工标注的适用规则中。对没有适用规则的案例，分别统计「检索仍给候选」与「模型仍引用」，定位问题发生在哪一段。分母为 0 的指标显示「不适用」。
- 配对结果单列「仅有 RAG 正确」「仅无 RAG 正确」「均正确」「均不正确」「请求未完成」。返回格式错误计为判断失败；接口错误不计作 RAG 胜败，结果仍落盘，运行报不完整。记录含检索的响应耗时中位数，不把失败请求当作低延迟。
- 这是固定案例的选项判断评测，测的是**同一输入注入检索上下文**的差别，不测 Agent 如何选择什么时候查库，也不评价解释文本的全部事实。选项和样本量限制了外推；若两组均分高或差距小，不能声称 RAG 显著改进。上游检索仍沿用当前索引后端，不因此宣称启用了语义检索。

## 验证状态

离线验证已覆盖冻结案例及规则 ID 检查、候选上下文隔离、真实检索产生的适用及无关候选、错误引用和请求异常记分。离线测试使用固定输出，只验证评测程序，不代表模型得分。

### 真实模型实测（2026-11-14，Asia/Shanghai）

模型 `deepseek-chat`，索引 178 条、纯关键词 Top-5。先独立完成一次共 14 对的首跑，再另起一次实验，对同 14 个案例各测两次，第二次将每一对的先后顺序反转。下表使用独立复跑的 28 对（56 个响应），不把首跑计入汇总，也不把重复的案例当作新题。

| 指标 | 无 RAG | 有 RAG |
| --- | ---: | ---: |
| 选项正确（不判断是否暂缓字段） | 28/28 | 28/28 |
| 选项和是否暂缓均正确 | 27/28 | 21/28 |
| 应暂缓时选项和标记均正确 | 15/16 | 9/16 |
| 有效且适用的引用 / 所有引用 | 不适用 | 26/30 |
| 正确且依据有效 / 有适用规则进入候选 | 不适用 | 13/22 |
| 无适用规则却引用规则 | 0/6 | 2/6 |
| 无适用规则但仍检出候选 | 不适用 | 6/6 |
| 获得响应的耗时中位数（含检索） | 904 ms | 923 ms |
| 输出格式失败 / 接口请求失败 | 0 / 0 | 0 / 0 |

配对：仅有 RAG 正确 0 对，仅无 RAG 正确 6 对，两组均正确 21 对，两组均不正确 1 对。独立首跑的联合判断同方向（无 RAG 13/14，有 RAG 10/14）；选项仍是两组都是 14/14。此次 RAG **没有提高选项正确率**；联合判断的差异来自模型的 `abstain` 标记，而非它改变了所选处置，不能表述为 6 次清洗建议错误。例：量程边界用例中，两组均选择「先核对校准、状态码与实验记录」，但有 RAG 的模型把该选项标成了不需暂缓。另一类是真正的引用适用性错误：即使说明明确 `999` 是有效分，也出现了引用缺失哨兵规则。

当前结果支持先处理两项小问题：候选资料与本批的数据字典冲突时必须忽略；模型选了等待确认的处置时，将产品的「等待确认」状态取自结构化处置，避免依赖另一个可能矛盾的标记。这里没有调整 Prompt、检索或金标来追高分。下一次应先冻结一批新的未见案例，再验证规则候选的筛选或回答口径的修复。

本机保留首跑 `.tmp/rag-comparison/2026-11-14T11-21-08-875Z/` 和独立复跑 `.tmp/rag-comparison/2026-11-14T11-23-06-241Z/` 的原始运行产物。公开复核用的去自由文本记录见 [eval-rag-comparison-runs.json](eval-rag-comparison-runs.json)；包含模型选项、标记、候选和引用，能复算分数。

`/export` 的「系统准确率」卡片单独折叠显示这轮实测的五项计数，数据来自 [eval-rag-comparison.json](eval-rag-comparison.json)。离线测试从上面的逐例记录和固定案例标注复算并核对这五项。
