## 2. 字段定义

Excel 里一行 = 一条规则。**「类别」由所在 sheet 决定**，因此没有独立的类别列。

| 列 | 必填 | 类型 | 约束 |
| --- | --- | --- | --- |
| `id` | 是 | 字符串 | 唯一；仅允许 `[a-z0-9-]`；同一规则的修订**不得改 id** |
| `标题` | 是 | 字符串 | ≤ 30 字；不含换行 |
| `适用学科` | 是 | 枚举 | `通用` 或学科名（`心理学`/`教育学`/`公共卫生`/…） |
| `适用字段` | 否 | 字符串 | 逗号分隔的列名别名；**留空 = 任何列都适用** |
| `触发条件` | 是 | 字符串 | 一句话说明何时该用；≤ 60 字 |
| `规则内容` | 是 | 字符串 | 2–5 句；禁止出现「同上」「略」「见上」 |
| `正例` | 否 | 字符串 | 多个用 `；` 分隔 |
| `反例` | 否 | 字符串 | 同上。**归并类规则必填** |
| `来源` | 是 | 字符串 | 不得为空；不确定时写「待确认」 |
| `权威度` | 是 | 枚举 | `国标` / `行业` / `团队经验` |
| `核验状态` | 是 | 枚举 | `已核对` / `待核对` |

### 三个设计决定的理由

**为什么「类别」由 sheet 决定，而不是单独一列**
Excel 里多一列就多一个填错的机会，而 sheet 归属在物理上不可能填错。放错 sheet 由转换脚本报错即可。

**为什么 `适用字段` 留空表示「任何列都适用」**
缺失编码、全角字符这类规则不针对特定字段，它们对每一列都成立。留空语义上等于「泛化规则」：检索时**不参与字段名过滤**，始终作为候选参与排序。若强行要求填字段名，会逼着填写者写「任意列」这种假值，反而污染字段名索引。

**为什么 `来源` 不允许为空**
答辩要能逐条追溯规则出处。「不确定」是允许的状态（写「待确认」），「没想过」不是。空值一律退回。

## 3. 转换时的校验规则

`build-index.py` 遇到下列情况**报错并中止**，输出「sheet 名 + 行号 + 字段名 + 原因」：

| 校验 | 原因 |
| --- | --- |
| `id` 重复 | 后者会静默覆盖前者 |
| `id` 含非法字符 | 会出现在索引文件名与 URL 里 |
| `来源` 为空 | 无法追溯 |
| `标题` / `触发条件` / `规则内容` 为空 | 检索不到或检索到也没用 |
| `规则内容` 含「同上」「略」「见上」 | 片段脱离上下文后不自洽 |
| `权威度` / `核验状态` 不在枚举内 | 排序与筛选会失序 |
| 归并类条目的 `反例` 为空 | 缺反例是误合并的主要来源 |
| sheet 名不是三个已知类别之一 | 类别无法推断 |

**警告（不中止，但会列出来）**：

- `适用字段` 只有一个别名，且该别名不是常见叫法 → 很可能召不回
- `核验状态 = 待核对` → 汇总成待办清单
- 同一 `适用字段` 别名被多条规则声明 → 提示可能有重复规则

## 4. 产物格式

### `entries/<学科>.yaml`

```yaml
- id: general-missing-negative-code
  标题: 负数编码表示未回答
  类别: 数据标准          # 由 sheet 推断
  适用学科: 通用
  适用字段: []            # 留空 → 空数组
  触发条件: 该列为数值列且出现负数取值时
  规则内容: |
    国内大型调查数据常用负数区分未回答的原因……
  正例: -9 需按码表判定
  反例: -3 拒绝回答，与「不知道」是不同机制，不可简单合并
  来源: 国内社会科学调查数据的常见约定，具体码表待按数据集说明核对
  权威度: 行业
  核验状态: 待核对
```

### `index/rules.json`

```jsonc
{
  "builtAt": "2026-10-12T10:00:00.000Z",
  "model": "bge-small-zh-v1.5",
  "entries": [
    {
      "id": "general-missing-negative-code",
      "学科": ["通用"],
      "适用字段": [],
      // 用于稠密检索：标题 + 触发条件 + 规则内容 的拼接
      "embedding": [0.013, -0.221, /* … 512 维 */],
      // 用于稀疏检索：条目全文的字符 2-gram 词频
      "sparse": { "负数": 3, "编码": 2, "数编": 1 }
    }
  ]
}
```

**向量在构建期算好**，不放在运行时：浏览器只需对查询算一次向量，避免加载时批量推理。这也让「同一份模型版本」成为构建产物的属性，稠密与稀疏的分数量纲不会漂移。

## 5. 检索时的过滤与排序

```
查询 = 当前数据的列名 + 类型 + 疑似同义组 + 高频取值（见 Plan 2 的 buildDataSummary）
   ↓
候选集 = { 学科 ∈ {通用, 用户选中的学科} }
   ↓
┌────────────────────────┬────────────────────────┐
│ 稠密：余弦相似度          │ 稀疏：字符 2-gram + BM25  │
│ 仅对候选集算             │ 仅对候选集算             │
└───────────┬────────────┴───────────┬────────────┘
            └──────────┬─────────────┘
                  RRF 融合（k = 60）
                       ↓
          列名精确命中 `适用字段` 的条目加权
                       ↓
                  Top-K（默认 5）注入 Prompt
```

**为什么要给列名命中加权**：`适用字段` 是人工维护的强信号。`GB/T 2260` 这类专有名词向量检索不敏感，而列名「行政区划」能精确命中 —— 这是混合检索之外最便宜、最可靠的一路。

**`适用字段` 留空的条目如何加权**：不加权，但也不被过滤掉。它们靠语义相似度竞争，避免泛化规则淹没专门规则。
