# 知识库字段定义与技术要求

> 这份是**技术规格**，写给转换脚本和维护者看。
> 团队只需要看 [`README.md`](README.md)，不必细读本文。

## 1. 目录结构

```
knowledge/
  README.md                     ← 团队填写说明
  schema.md                     ← 本文
  知识库模板.xlsx                ← 团队填写的唯一载体（源文件；8 张 sheet，见下）
  tools/
    make-template.py            ← 生成「空白」填写模板的脚本（可重复运行；当前真源不是它的产物）
    build-index.py              ← xlsx → entries/*.yaml → index/rules.json（已实现）
  entries/                      ← 产物：机器读取的规则源文件（7 个学科各一个）
    general.yaml                ← 通用
    data-science.yaml           ← 数据科学与大数据技术
    psychology.yaml / education.yaml / public-health.yaml / sociology.yaml / economics.yaml
  index/                        ← 产物：浏览器运行时加载
    rules.json                  ← 条目原文 + 稠密向量 + 稀疏词频
    field-alias-taxonomy.json   ← 两级标签体系（学科 → 字段别名组），供列名加权与人工复查
  reports/                      ← 产物：构建报告
    build-report.md             ← 团队看的那份
    build-report.json           ← 机器读的那份
```

**单一真源是 `知识库模板.xlsx`。** `entries/`、`index/`、`reports/` 都是产物，不要手改 —— 手改会在下次转换时被覆盖。`build-index.py` 每次全量重写这三处（包括删掉 `entries/` 下上一次留下的孤儿 yaml），不做增量更新：增量更新是「产物与真源不一致」的主要来源。

**工作簿的 8 张 sheet**：3 张填写表（数据标准 / 口径规则 / 清洗案例）+ 5 张文档性 sheet（填写说明 / 字段说明 / 修订核验记录 / 本次扩展导航 / 学科目录）。文档性 sheet 在 `build-index.py` 的 `IGNORED_SHEETS` 里**逐项显式登记**，不放宽成「未知 sheet 一律跳过」——否则填写表名字拼错会被静默忽略、少构建一批条目。新增文档性 sheet 必须同步登记，否则构建以「未知 sheet」中止。

## 2. 字段定义

Excel 里一行 = 一条规则。**「类别」由所在 sheet 决定**，因此没有独立的类别列。

| 列 | 必填 | 类型 | 约束 |
| --- | --- | --- | --- |
| `id` | 是 | 字符串 | 唯一；仅允许 `[a-z0-9-]`；同一规则的修订**不得改 id** |
| `标题` | 是 | 字符串 | ≤ 30 字；不含换行 |
| `适用学科` | 是 | 枚举 | 7 选一：`通用` / `数据科学与大数据技术` / `心理学` / `教育学` / `公共卫生` / `社会学` / `经济学`；每条只填一个 |
| `适用字段` | 否 | 字符串 | 逗号分隔的列名别名；**留空 = 任何列都适用** |
| `触发条件` | 是 | 字符串 | 一句话说明何时该用；≤ 60 字 |
| `规则内容` | 是 | 字符串 | 2–5 句；禁止出现「同上」「略」「见上」 |
| `正例` | 否 | 字符串 | 多个用 `；` 分隔 |
| `反例` | 否 | 字符串 | 同上。**归并类规则必填** |
| `来源` | 是 | 字符串 | 不得为空；不确定时写「待确认」。**可以包含一行公开 URL 与一行日期**（推荐三行：依据名称 → 公开 URL → `核对日期：YYYY-MM-DD`；「资料查阅日期」「复核日期」也认）；界面会提取**第一个 URL** 作为可点击来源链接（解析规则见下文） |
| `权威度` | 是 | 枚举 | `国标` / `行业` / `团队经验` |
| `核验状态` | 是 | 枚举 | `已核对` / `待核对` |

### 三个设计决定的理由

**为什么「类别」由 sheet 决定，而不是单独一列**
Excel 里多一列就多一个填错的机会，而 sheet 归属在物理上不可能填错。放错 sheet 由转换脚本报错即可。

**为什么 `适用字段` 留空表示「任何列都适用」**
缺失编码、全角字符这类规则不针对特定字段，它们对每一列都成立。留空语义上等于「泛化规则」：检索时**不参与字段名过滤**，始终作为候选参与排序。若强行要求填字段名，会逼着填写者写「任意列」这种假值，反而污染字段名索引。

**为什么 `来源` 不允许为空，并且现在鼓励写成「依据名称 + 公开 URL + 核对日期」三段**
答辩要能逐条追溯规则出处。「不确定」是允许的状态（写「待确认」），「没想过」不是。空值一律退回。
2026-10-25 的多学科扩展版起，能引公开文档的条目把来源写成三行：依据名称、可点开的 URL、日期行（实际混用「核对日期」56 条、「资料查阅日期」64 条、「复核日期」1 条，三种都表示团队看过这条来源）。
URL 让评审当场回查，日期行说明核到哪一天。界面的「来源链接 / 核验日期」**不另设列**，而是
`src/ui/lib/ruleSource.ts` 从来源原文里取**第一个 URL** 作为可点击链接、取日期行（核对/资料查阅/复核日期）作为核验日期；
解析不到就显示「未提供」，不在索引里替条目补造字段
（写成「资料查阅日期」等其它标签不会被识别）。单行来源仍然合法 —— 历史条目与没找到公开链接的条目都这么写。

### `权威度` 三个档位的实际含义（曾经被当成垃圾桶用过）

一开始几乎全部标了「行业」，但那不成立 —— 一批没有标准可引的条目顶着「行业」，
是拿模糊来源撑具体等级。现在的判据是**依据能否追到一个成体系的方法学或官方文档规范**：

| 档位 | 什么时候用 | 典型来源 |
| --- | --- | --- |
| `国标` | 能给出可核对的国标／行标编号 | `行政区划代码国家标准（GB/T 2260…）` |
| `行业` | 依据来自一个成体系的领域方法学，可以引用而不必自证 | `统计学基本口径`、`机器学习工程的通用约定`、`统计指标口径的通用约定` |
| `团队经验` | **没有可引的外部权威** —— 依据是软件的可复现行为、格式规范的实际表现，或领域通行做法 | `Excel 数据交换的已知行为`、`CSV 格式的已知解析行为`、`数据清洗通用约定` |

> **`团队经验` 在这里的含义是「无外部权威可引、由本团队采纳」，不是「我们跑过这批数据」。**
> 后者是 `来源` 列要讲的事，两者不要混。混淆会直接造出一个答辩答不上来的假出处
> （模板预填里有 3 条就写着「我们自己跑数据时发现」，已改掉）。

判据落在代码里是 `build-index.py` 的两个来源白名单（`INDUSTRY_SOURCES` / `NATIONAL_STANDARD_SOURCES`），
**外加 2026-10-25 多学科扩展版补的两种可核对证据**：`行业` 的来源里带公开 URL 也算数，`国标` 的来源里出现 GB 编号也算数。
旧白名单保留，用来兜住没有 URL 的历史条目；两者都不命中才是 `团队经验`。
**新条目用单行来源标「行业」时，得先把依据类型加进白名单** ——
这是一个刻意的摩擦，防止「行业」再变成默认值；带 URL 的来源不需要改代码，URL 本身就是可回查的证据。

## 3. 转换时的校验规则

`build-index.py` 遇到下列情况**报错并中止**，输出「sheet 名 + 行号 + 字段名 + 原因」：

| 校验 | 原因 |
| --- | --- |
| `id` 重复 | 后者会静默覆盖前者 |
| `id` 含非法字符 | 会出现在索引文件名与 URL 里 |
| `来源` 为空 | 无法追溯 |
| `标题` / `触发条件` / `规则内容` 为空 | 检索不到或检索到也没用 |
| `规则内容` 含「同上」「略」「见上」 | 片段脱离上下文后不自洽 |
| `权威度` / `核验状态` 不在枚举内 | 排序与筛选会失序 |
| 归并类条目的 `反例` 为空 | 缺反例是误合并的主要来源 |
| sheet 名不是三个已知类别之一 | 类别无法推断 |

**警告（不中止，但会列出来）**：

- `适用字段` 只有一个别名，且该别名不是常见叫法 → 很可能召不回
- `核验状态 = 待核对` → 汇总成待办清单
- **`权威度` 与 `来源` 对不上** → 见下
- 同一 `适用字段` 别名被**同一类别**的多条规则声明 → 冗余的可能性较高，需逐条确认
- 同一 `适用字段` 别名被**跨类别**的多条规则声明 → **只汇总成一行报数量，不逐条刷**。
  标准讲取值规范、口径讲怎么算、案例讲踩过的坑，同一字段由三处分别覆盖是约定的分工

**`权威度` 必须与 `来源` 对得上**（三个方向的检查）：

| 情况 | 提示 |
| --- | --- |
| 标了 `国标` 但来源不在国标清单里 | 来源里也没有可核对的 GB 编号 —— 补上标准号，或改标 `行业` |
| 标了 `行业` 但来源不在行业清单里 | 来源里也没有公开 URL —— 补一个可回查的链接（或把依据类型加进白名单），够不上就改标 `团队经验` |
| 标了 `团队经验` 但来源是可引用的方法学依据 | 这条其实够得上 `行业` |

这条检查是**加出来的**，起因是：一开始整批条目都被默认标成「行业」，那个档位等于没有信息量。
清单写在 `build-index.py` 的 `INDUSTRY_SOURCES` / `NATIONAL_STANDARD_SOURCES`，
新条目用单行来源标「行业」得先把依据类型加进清单 —— **刻意的摩擦**，防止「行业」变回默认值；
2026-10-25 多学科扩展版把来源写成「依据名称 + URL + 核对日期」后，判据放宽为「命中旧清单**或**来源带公开 URL」
（`国标` 同理：来源里出现 GB 编号也算可核对），否则那 120 条带 URL 的来源会被整批误报成警告，真信号反而被淹掉。

> 这条检查立刻抓到了一处真问题：我在两个脚本里各抄了一份清单，其中一份把「待团队**对照**原文」
> 抄成了「待团队**核对**原文」，于是两条条目的权威度被判成了 `团队经验`。
> **同一份清单抄两份必然漂移** —— 这也是它值得做成检查而不是靠人记的原因。

### 实现时的四处收窄（避免误报把真信号淹掉）

规格里的判据在落到代码时都要收窄，否则会产出大量假警报把真信号埋掉。四处：

| 判据 | 裸实现的问题 | 实际做法 |
| --- | --- | --- |
| `规则内容` 含「略」 | 「策略」「忽略」「省略」都是正常用词 | 见下方「收窄踩过三次坑」。最终只排除**以「略」结尾的常见词**（`LUECED_COMPOUND_TAILS`） |
| 非三个已知 sheet 即报错 | 模板自带 5 张文档性 sheet（填写说明 / 字段说明 / 修订核验记录 / 本次扩展导航 / 学科目录） | 用显式白名单（`IGNORED_SHEETS`）而不是「非数据表即跳过」——后者会让团队误建的 sheet 被静默忽略 |
| `适用字段` 留空即警告 | 留空是第 2 节明确设计的「泛化规则」语义，24 条合法条目会各出一条噪音 | 不报警告，改为在报告与 `field-alias-taxonomy.json` 里单独统计泛化规则数 |
| 别名被多条规则声明即警告 | 47 条规则时会刷出 32 条，其中大部分是约定分工 | 按**类别**拆分：同类别内逐条报（冗余可能性高），跨类别只汇总一行报数量。收窄后是 9 条 |

**另有一条硬校验（规格未写但必须有）**：`适用学科` 必须是已登记 slug 的学科名。未登记的学科名会让构建失败并提示去 `SUBJECT_SLUGS` 登记 —— 用拼音自动转换会产生「同一个学科两种拼法」这类只能靠人发现的错。当前已登记 **7 个**：`通用`、`数据科学与大数据技术`、`心理学`、`教育学`、`公共卫生`、`社会学`、`经济学`（依次对应 `entries/` 下的 `general` / `data-science` / `psychology` / `education` / `public-health` / `sociology` / `economics`；当前通用 126 条、学科专属 52 条）。

### 「略」的收窄踩过三次坑

这条校验看着简单，实际收窄了三轮，每一轮都是被真实数据打回来的：

| 轮次 | 写法 | 结果 |
| --- | --- | --- |
| 1 | 裸匹配「略」 | 命中「策略」「忽略」「省略」等正常用词，误报一片 |
| 2 | 只匹配「略。」 | **仍然命中「再决定填补策略。」** —— 被构建拦下的正是我们自己写的一条规则 |
| 3 | 要求「略」前面不是汉字 | 「此处略。」这种真占位反而漏掉了（「处」也是汉字） |
| 现在 | 只排除以「略」结尾的常见词的**最后一个字** | 「策略。」不命中，「此处略。」命中 |

**由此得出一条通用做法：为防误报而收窄正则时，必须同时准备「真阳性仍然命中」的测试。**
只测不误报，收窄会一路滑成放水。`--self-test` 里现在两个方向都有断言
（正常用词 3 例必须放过、真占位 3 例必须抓到），共 54 项。

**构建脚本可自测**：`build-index.py --self-test` 内嵌 39 项断言，覆盖全部错误判据的正反例、空行跳过、YAML 往返保内容、向量确定性与归一化、2-gram 跨空白、`rules.json` 回读自检（含「篡改后必须报错」的反例，确保这道关有牙齿）。改动该脚本后必须跑它（Python 工具链跑不进 Vitest，所以测试内嵌在脚本里）。

## 4. 产物格式

### `entries/<学科>.yaml`

```yaml
- id: general-missing-negative-code
  标题: 负数编码表示未回答
  类别: 数据标准          # 由 sheet 推断
  适用学科: 通用
  适用字段: []            # 留空 → 空数组
  触发条件: 该列为数值列且出现负数取值时
  规则内容: |-
    国内大型调查数据常用负数区分未回答的原因……
  正例: -9 需按码表判定
  反例: -3 拒绝回答，与「不知道」是不同机制，不可简单合并
  来源: 国内社会科学调查数据的常见约定，具体码表待按数据集说明核对
  权威度: 行业
  核验状态: 待核对
```

四点实现说明：

- **块标量用 `|-` 而不是 `|`。** 源单元格里没有行尾换行，`|`（clip）会补一个；`|-`（strip）才能原样往返。
- **`来源` 可以是多行。** 2026-10-25 版把它写成三段（依据名称 / 公开 URL / `核对日期：YYYY-MM-DD`），yaml 用块标量原样保留换行，`rules.json` 也按原文保留；界面从原文里解析第一个 URL 与日期行（核对/资料查阅/复核日期，见第 2 节），不在索引里另造字段。
- **脚本自证往返。** 写完会重载一遍比对每个字段；一旦块标量改变了取值，就退回默认引号写法重新输出。宁可不漂亮，也不改内容。
- **文件不含时间戳。** 让同一份 Excel 两次构建产出逐字节相同的 yaml，git diff 里出现的变化一定对应真实的内容改动（时间戳只进 `rules.json` 与报告）。

### `index/rules.json`

```jsonc
{
  "builtAt": "2026-10-13T00:04:03Z",   // 设了 SOURCE_DATE_EPOCH 时用它，便于可复现构建
  "model": "char-ngram-hash-512-v1（离线降级后端…）",
  "dim": 512,
  "rrfK": 60,
  "topK": 5,
  "entries": [
    {
      "id": "general-missing-negative-code",
      "学科": ["通用"],
      "适用字段": [],
      // 条目原文。检索命中后要注入 Prompt，所以正文必须在这里 ——
      // 只存 id 的索引在运行时没法用。
      "entry": { "标题": "…", "类别": "…", "触发条件": "…", "规则内容": "…", "正例": "…", "反例": "…", "来源": "…", "权威度": "…", "核验状态": "…" },
      // 用于稠密检索：标题 + 触发条件 + 规则内容 的拼接
      "embedding": [0.013, -0.221, /* … 512 维，L2 已归一化，6 位小数 */],
      // 用于稀疏检索：条目全文（标题+别名+触发条件+规则内容+正例+反例）的字符 2-gram 词频
      "sparse": { "负数": 3, "编码": 2, "数编": 1 }
    }
  ]
}
```

**向量在构建期算好**，不放在运行时：浏览器只需对查询算一次向量，避免加载时批量推理。这也让「同一份模型版本」成为构建产物的属性，稠密与稀疏的分数量纲不会漂移。

**条目原文不能省。** 上面的 `entry` 字段是原规格示例里漏画的 —— 同段文字写的是「条目原文 + 稠密向量 + 稀疏词频」，但示例只有 id 与检索字段。运行时若拿不到正文，检索到也没东西可注入。

**向量数组压成一行。** 512 维按 `indent=2` 展开是 512 行，17 条就是 8704 行 —— 那种产物没法读，git diff 也看不出有意义的变化。脚本把「元素全是数字」的数组折成一行；含字符串的数组（如 `适用字段`）保持多行，因为别名要能一眼看清。

### `index/field-alias-taxonomy.json`

两级标签体系：一级 = `适用学科`，二级 = 字段别名组。

聚类依据只有一条：**共同出现在同一条规则里**（并查集的连通分量）。脚本不做任何同义判定 ——「学历」和「文化程度」是不是同一个字段是领域判断，该由填表的人决定；脚本只回答「你们已经把它们写在一起了，那它们就是一组」，并用 `依据` 字段记下是哪几条规则把它们连起来的，让结果可逐组回查。

若某组里同一条规则贡献了 ≥5 个别名，会加一个 `待确认` 字段，请团队判断这些别名是否属于同一字段族：`学号／工号／编号` 同族，`性别／学历／民族` 不同族。**脚本只提出疑问，不下结论** —— 靠字符 2-gram 分不出这两者（`学号` 与 `编号` 的字面重合度是 0）。

## 5. 构建脚本

```powershell
# 平时用这条：解析 → 校验 → 写 entries/index/reports
python knowledge/tools/build-index.py

# 只校验，不写任何文件（改完 Excel 想先确认能不能过）
python knowledge/tools/build-index.py --check

# 顺带跑自召回冒烟测试，并算进报告
python knowledge/tools/build-index.py --self-recall

# 改动本脚本后必须跑：39 项内嵌断言
python knowledge/tools/build-index.py --self-test

# 用真语义模型算向量（需先装 sentence-transformers，且要能下载模型）
python knowledge/tools/build-index.py --embedder bge
```

依赖：`openpyxl`（读 xlsx）、`PyYAML`（写 yaml）。缺依赖时脚本给安装命令，不抛堆栈。

### 两个向量后端

| 后端 | `model` 字段写什么 | 何时用 |
| --- | --- | --- |
| `char-ngram-hash`（默认） | `char-ngram-hash-512-v1（离线降级后端，非语义模型…）` | 任何环境都能跑：无网络、无模型下载、跨进程确定性 |
| `bge` | `BAAI/bge-small-zh-v1.5` | 需要真语义相似度时（`--embedder bge`） |

**为什么要有离线后端**：第 4 节要求向量在构建期算好，而构建不该依赖网络与 200MB 模型下载。缺模型时给一个「能跑的降级路径」，而不是「构建失败」—— 这与产品其它部分的处理方式一致（端侧 embedding 不可用 → 降级到结构化规则）。

**不冒名**：`model` 字段如实写出用了哪个后端。离线后端产出的是真实的稠密向量（哈希 2-gram 词袋 + L2 归一化，用 blake2b 而非内置 `hash()`，否则 `PYTHONHASHSEED` 随机化会让同一份输入两次构建产出不同索引），但不是语义模型 —— 换个说法它就不成立了。**换成 bge 后必须重跑自召回并重新调阈值**（阈值与模型强绑定，见设计文档 §5.5.4）。

### 阈值必须与后端匹配（踩过一次）

**余弦相似度的绝对尺度是后端的属性，不是文本的属性。** 语义模型的同义句余弦常在 0.9 以上，
而哈希 2-gram 的尺度被压得很扁 —— 实测 96 条共 4560 对，最大只有 0.38，中位数 0.046。

所以近重复阈值写死成单一个值会让某个后端下这个检查**永远沉默**。真出过一次：
阈值写死 0.86，离线后端下最大值才 0.38，于是「疑似近重复」长期显示 0，
看起来像「没有问题」—— 而一个常年报 0 的指标比没有指标更糟，它会让人以为已经检查过。

现在的做法有三条：

1. `NEAR_DUPLICATE_COSINE` 是**按后端取值的字典**（`char-ngram-hash` → 0.30，`bge` → 0.86）
2. 报告的第八节**无条件给出余弦分布（最大／p99／p90／中位）与最相似 TOP 5** ——
   即使一对都没过阈值也要给，否则读者分不清「真的没有重复」与「阈值根本够不着」
3. 当最大值低于阈值时，构建会把这件事**本身报成一条警告**，不让它静悄悄失效

0.30 是照实测分布定的，**没有标注集可校准**，因此既有漏报也有误报（实测 96 条标出 2 对：
1 对是真重叠，1 对是假阳性）。换 bge 后端后必须重定；Plan 4 建起评测集才谈得上校准。
报告里对这一点有明示，不要把阈值当判决看。

另外把后端标识符 `EMBEDDER_HASH` / `EMBEDDER_BGE` 放在文件顶部的常量区：
阈值表要按它们取值，若定义在文件后面，定义顺序就成了隐藏依赖（写错过一次，直接 `NameError`）。

### 模板的覆盖保护与默认页

`make-template.py` 是**覆盖式**写文件的，而模板是团队填写的唯一真源。所以它默认会检查
「每张填写表的条目数是否多于预填条数」，一旦多于就**拒绝重建**并列出差异，确需重建要显式加 `--force`。
理由：xlsx 是二进制，git diff 不出丢了什么，误跑一次就是静默的数据丢失。

`make-template.py` 生成（重建）的模板打开时**停在「数据标准」**而不是第一张「填写说明」。便签页只有几行字，
扫一眼会以为表格是空的（这真的发生过）。这条同时写在 `make-template.py` 里，保证脚本重建后行为一致。

> **注意：当前真源不是这个脚本的产物。** `knowledge/知识库模板.xlsx` 现在是团队交付的 8-sheet 多学科扩展版
> （178 条、7 个学科），打开时停在「填写说明」，且三张填写表末尾没有预留带边框的空行。
> 所以**不要用 `make-template.py` 重建当前真源**：它只会生成 3 张填写表 + 2 张便签的空白模板，
> 覆盖已填写的工作簿等于静默丢数据。若确需重建，以真源结构为准，并另行补齐 3 张扩展说明 sheet。

### `reports/build-report.md`

团队看的那份，内容：结论 → 分布 → 错误 → 警告 → 待核对清单 → 入库质量分 → 字段别名体系 → 疑似近重复 → 自召回指标。

当前这份（2026-10-25 多学科扩展版）：178 条、0 错误、36 警告、待核对 74 条；
自召回 Hit@1 0.8427 / Hit@5 0.9663 / MRR 0.8979；同科近重复 1 对（0.3037，阈值 0.3）。

两条口径要留意：

- **入库质量分是扣分制**，7 个可核查的项（定义见 `build-index.py` 的 `QUALITY_ITEMS`）。不给「综合评分」这类黑箱数字 —— 团队要知道改哪里能把分提上去。
- **自召回是冒烟测试，不是质量评测。** 它只能发现「索引坏了」（别名没进索引、学科过滤写反、向量没算），发现不了「规则本身写得不好」。真实评测需要团队标注的「数据摘要 → 规则」对，见设计文档 §5.9。

## 6. 检索时的过滤与排序

```
查询 = 当前数据的列名 + 类型 + 疑似同义组 + 高频取值（见 Plan 2 的 buildDataSummary）
   ↓
候选集 = { 学科 ∈ {通用, 用户选中的学科} }
   ↓
┌────────────────────────┬────────────────────────┐
│ 稠密：余弦相似度          │ 稀疏：字符 2-gram + BM25  │
│ 仅对候选集算             │ 仅对候选集算             │
└───────────┬────────────┴───────────┬────────────┘
            └──────────┬─────────────┘
                  RRF 融合（k = 60）
                       ↓
          列名精确命中 `适用字段` 的条目加权
                       ↓
                  Top-K（默认 5）注入 Prompt
```

**为什么要给列名命中加权**：`适用字段` 是人工维护的强信号。`GB/T 2260` 这类专有名词向量检索不敏感，而列名「行政区划」能精确命中 —— 这是混合检索之外最便宜、最可靠的一路。

**`适用字段` 留空的条目如何加权**：不加权，但也不被过滤掉。它们靠语义相似度竞争，避免泛化规则淹没专门规则。

`FIELD_HIT_BOOST` 取 `0.05` 的依据：RRF（k=60）下单路排序第一名的贡献是 `1/61 ≈ 0.0164`，三路齐第一也才 `0.049`。取 0.05 相当于「列名命中」约等于多给了一整路排序器的头名权重 —— 是一个有参照的量级，不是随手拍的数字。**它仍未经过标注集调优**，Plan 4 建起评测集后应重新扫。

同样的，`RRF_K`、`BM25_K1`、`BM25_B`、`TOP_K`、近重复余弦阈值 0.86 都写在 `build-index.py` 顶部的常量区，一起集中调。
