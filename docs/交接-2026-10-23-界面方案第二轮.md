## 2 五项改动的落点

### 2.1 执行前改参预览

- 新增 [`impactPreview.ts`](../src/ui/lib/impactPreview.ts)：调用 core 的
  `applyCleaningActions` **在内存里试算**，不写任何 store。输出
  「改多少单元格 / 删多少行 / 多少条动作无法执行」。
- 关键口径：core 在删行时把 `changedCells` 记成行数差；直接求和会出现
  「改动 5 格、删除 5 行」的重复计数。所以只累计 `before.rowCount === after.rowCount`
  的动作，删行单独报。
- 界面位置：[`IssueReview.tsx`](../src/ui/components/IssueReview.tsx) 的「执行清洗」按钮上方，
  `data-testid="cleaning-preview"`；只在未执行、版本未失效时显示。

### 2.2 运行中停止 + 按失败环节重试

- [`AgentPanel.tsx`](../src/ui/components/AgentPanel.tsx) 在 `busy` 时显示「停止分析」，
  调 AI SDK v7 的 `stop()`；停止后给一句可读说明（已产生的记录与结论保留），
  并用一个只认 `stopped` 的 effect 拦住 SDK 客户端工具结果触发的自动续跑。
- 失败时用纯函数 `failureRetryPhase(messages)`（[`agentPhase.ts`](../src/ui/lib/agentPhase.ts)）
  从消息派生失败环节（planning / execution / synthesis），按钮为
  「从制定检查计划重试 / 从执行检查重试 / 从汇总问题重试」，点击发一条
  **该环节的续跑指令**（明确要求已完成的检查与列画像不要重做），而不是笼统地
  `regenerate()` 从头重来。
- 提交分析改为 `beginRun(useDatasetStore.getState().dataVersion)`，审阅结论开始绑版本。

### 2.3 旧结论按数据版本显式失效

- `dataVersion` 从展示字段变成真正状态：
  - 载入/恢复时随 IndexedDB 缓存落盘（`CACHE_VERSION` 1 → 2），恢复沿用落盘版本，
    不再刷新后归 0；
  - 每次执行清洗或撤销 +1；`checksVersion` 记录问题清单算在哪一版上；
  - 检查/审阅/AI 分析各自记录自己基于哪一版（`checksVersion`、`reviewStore.runVersion`）。
- 数据一变，旧清单**立刻从当前位置撤下**（`issues: []`、`checksStatus: running`），
  不会出现「旧结论挂着、数字却是新的」；检查完成后再绑定新版本。
- 界面：`DataContextBar` 增加「原始数据 / 清洗后数据」与「检查结论属于 vX」徽章；
  检查页按新版本重画；分析页在「未执行、数据已变」时提示旧结论失效；
  导出页显示数据版本并提示旧检查结论。
- **版本语义**：`dataVersion` 是「当前工作数据」的修订号，不是导入次数。
  清洗结果与撤销不写回 IndexedDB（缓存仍只存导入数据），刷新后回到导入版本 ——
  这是有意取舍，避免「缓存里一半是清洗后数据」这种两个真相。

### 2.4 撤销后重新检查联动

- `provenanceStore.undo()` 回退数据后，导出页调用
  `datasetStore.syncWorkingDataset(reverted)`：版本 +1、清空旧清单、后台重算画像 +
  语义归并 + 确定性检查；并 `reviewStore.reset()` 清掉对旧数据说的 AI 建议。
- 检查页表格标题随状态变为「原始数据 / 清洗后数据」，并保留「原始数据仍可撤销」的说明。

### 2.5 移动端底部操作区 + 768–1279 侧栏收起

- [`IssueReview.tsx`](../src/ui/components/IssueReview.tsx)：操作区在 <768px
  `fixed bottom-0`，`md:` 起回到文档流；卡片底部留占位，避免遮挡最后几条。
- 新增 [`SidebarFrame.tsx`](../src/ui/components/SidebarFrame.tsx)：
  768–1279px 可用「收起导航 / 展开导航」；≥1280 固定侧栏（收起入口隐藏）。
- 44px 有效点击区、长文本展开仍属第三轮，本轮没有改。

## 4 不能破坏的约定（在本轮基础上新增）

1. **数据版本是工作数据的修订号**：载入 +1、清洗/撤销 +1；恢复沿用落盘版本。
   不要把「刷新后版本归零」改回来 —— 那会让旧结论的标注失去意义。
2. **清洗后检查的是 `workingDataset`，不是 `parseResult.dataset`**：
   原始数据必须保留（导出指纹算在它上面、检查页要能说清看的是哪一版）。
3. **旧结论撤下而不是并存**：版本一变先 `issues: []` + `checksStatus: running`；
   不要为了「不闪一下空列表」而继续显示旧清单。
4. **预览只能调 core 纯函数**：`previewCleaningImpact` 绝不能调用
   `provenanceStore.apply`，否则预览会真的改数据。
5. **E2E 锁住的文案**：`执行清洗（N 条）`、`cleaning-outcome` 内文、
   `开始分析 / 分析中…`、检查计划复选框 aria-label、审核按钮名、表尾 `共 N 行 × M 列`。
6. **测试数字与文档同步**：722 / 8 / 63 与 77 / 1；改数量要同时改
   `docs/技术文档.md`、`docs/开发交接说明.md`、`docs/交接-2026-10-21.md`、
   本文件与 `scripts/check-doc-facts.mjs`，然后 `pnpm doc:build` + `pnpm check:doc`。

## 5 已知留存风险

- **~~失败重试发的是新 user message~~ 已修（2026-10-23）**：若失败恰好停在「工具输入完整、
  结果未回填」，AI SDK 会报 `MissingToolResultsError`。现在所有发送（重试/表单/按计划执行）
  都会先把残留的工具调用补成 `output-error` 再发；同时把该错误归一化成中文
  「上一次分析没有正常收尾」。回归 E2E「工具调用中断后再次发送，不会报 Tool results are missing」钉住。
- **停止按钮的窄屏布局**没有单独 E2E（只有底部操作区有）；真机未验。
- **移动端底部条按当前文案高度估算占位**（`h-40`），文案变长要同步调。
- **版本持久化只到导入版本**：清洗/撤销的版本不落盘；刷新后数据回到导入状态，
  这是与「缓存只存 Dataset」配套的取舍。
- 语义归并线上仍为 char-ngram 哈希后端，检查页降级提示照旧（第三轮/历史事项）。
