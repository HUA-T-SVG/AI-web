## 二、这台机器的特殊情况（重要）

这些在通用文档里查不到，但不知道就会卡住。

| 事项 | 说明 |
| --- | --- |
| **C 盘空间紧张** | 只剩约 30 GB，所有安装必须落 D 盘。执行 pnpm 前先设 `$env:TEMP='D:\tmp'; $env:TMP='D:\tmp'` |
| **Playwright 浏览器在 D 盘** | 跑端到端测试前设 `$env:PLAYWRIGHT_BROWSERS_PATH='D:\ms-playwright'`，否则会报找不到浏览器 |
| **git 用了 schannel 后端** | `D:\git\Git\etc\gitconfig` 里 `sslBackend = schannel`。原来的 openssl 因 CA 证书包过期连不上 GitHub。备份在同目录 `.bak-*` |
| **pnpm 12 会报 ERR_PNPM_IGNORED_BUILDS** | **可以忽略**。那是 pnpm 拦截 postinstall 的安全策略，本项目依赖的平台二进制走 optionalDependencies，不受影响 |
| **npm 全局目录在 C 盘** | `npm install -g` 会装到 C 盘。需要全局 CLI 时用 `pnpm` 或直接 `npx` |
| **PowerShell 执行策略** | `.ps1` 脚本可能被拦（如 `tsc.ps1`）。改用 `.cmd` 版本，例如 `node_modules/.bin/tsc.cmd` |
| **门禁脚本的坑** | 不要写 `pnpm test 2>&1 \| Select-Object -First N` —— PowerShell 会提前关闭管道并掐断 pnpm，把通过的测试记成失败。先存变量再过滤 |
| **`next-env.d.ts` 会来回抖** | 跑 `pnpm build` 与 `pnpm dev` 会让它在 `.next/types/` 与 `.next/dev/types/` 之间切换。那是 Next 自动生成的，**不要提交它**，每次还原掉即可（`git checkout -- next-env.d.ts`） |
| **dev server 会锁住源码文件** | 开着 `pnpm dev` 时改 `src/` 下的文件，可能报 `ReplaceFileW EIO (Win32 1175)`。那是 Turbopack 的文件监听持有句柄，**不是磁盘坏了**。先停 dev server 再改，或重试一次 |
| **别用 shell 改源码** | `Get-Content -Raw` 读 UTF-8 文件会按本机 ANSI（GBK）解码，再 `Set-Content` 写回就把中文全弄乱、引号还会变成 `?`，文件语法直接崩。改代码只用编辑工具 |
| **临时产物别放进 `test-results/`** | Playwright 每次跑测试都会清空自己的输出目录，放在那里的截图之类会被无声删掉 |
| **读 UTF-8 文件时控制台可能乱码** | `Get-Content`/`Select-String` 输出中文乱码通常只是控制台编码问题，不是文件坏了。用读取工具确认，或先 `[Console]::OutputEncoding=[System.Text.Encoding]::UTF8` |

## 三、开发流程约定

前两个计划都是这样走的，建议延续。

### 每个计划走一遍

```
1. 写计划      → docs/superpowers/plans/YYYY-MM-DD-<名字>.md
                 每个任务按 TDD 组织：写失败测试 → 确认失败 → 实现 → 确认通过 → 提交
2. 建特性分支  → git checkout -b feat/<名字>
3. 逐任务执行  → 每任务结束跑门禁，通过才提交
4. 整分支审查  → 派一个全新上下文的审查者，只读检查整条分支
5. 修复         → Critical 与 Important 一次修完，每条都要有先失败后通过的测试
6. 合并         → git merge --no-ff，在合并结果上重新跑门禁，然后删分支
```

对应的 skill：`writing-plans` → `executing-plans` → `requesting-code-review` → `finishing-a-development-branch`。

### 提交前的四道门禁

```powershell
$env:TEMP='D:\tmp'; $env:TMP='D:\tmp'
$env:PLAYWRIGHT_BROWSERS_PATH='D:\ms-playwright'

& node_modules/.bin/tsc.cmd --noEmit   # 类型
pnpm test                              # 单元测试
pnpm test:e2e                          # 端到端（含 .tsx 改动时）
pnpm build                             # 构建
```

**typecheck 必须当门禁**。Plan 1b 执行时有一次把 typecheck 和 commit 放在同一段脚本却没拿它做判断，结果一个类型错误被提交进去了。

### 合并用 `--no-ff`

比赛要求「保留完整 Git 提交历史，体现真实的开发过程」。合并提交让历史读起来是「功能分支 → 审查 → 合并」，而不是一堆平铺的 `update`。

**真实联调抓到的问题（这是本轮最有价值的部分）**：

| 问题 | 表现 | 修法 |
| --- | --- | --- |
| 单次工具调用载荷过大 | 整份问题报告塞进一次 `submit_issues` 时，工具输入**永远流不完**（状态停在 `input-streaming`），`onToolCall` 从不触发，**用户一条结论都拿不到** | 改成一次提交一条（`submit_issue`），各文本字段加长度上限 |

**独立审查抓到的三条 Critical**（都是「原始数据出门」这条硬承诺的正向违反，而我在自己写代码时没看出来）：

| # | 问题 |
| --- | --- |
| C-1 | `describe_column` 把整个 `ColumnProfile` 当工具结果返回，里面是行序前五个值的**原文**。我在摘要那条路上专门避开了 `profile.samples`，却漏了工具结果这条通道 |

### 8.3.2 本轮会话（10-12 下半）做了什么：合并、补文档、知识库分工

### 8.4 会话里做出、但没写进代码的决定

| 决定 | 理由 |
| --- | --- |
| **侧边栏「结构抄抖音、风格不抄」** | 分组/图标/选中态的信息架构是标准的，该学；但深色背景+大图标+高饱和色是消费级内容 App 的语汇，用在科研数据工具上传递的信息是错的。评分表里「交互模式创新 7%」考的是交互方式是否超越传统，不是长得像哪个热门 App |
| **未实现的功能要留在界面上（禁用+标注）** | 直接不渲染会让人以为产品就这几个功能；只置灰不解释会让人反复点击 |
| **不用组件库 CLI** | shadcn 本质是复制源码进项目，我们只需要几个简单组件；引入会连带一套主题与几十个 CSS 变量，且其 registry 在境内访问慢。复杂交互后续直接用 Radix 原语 |
| **不用 SheetJS（`xlsx`）** | npm 上的版本停在 0.18.5，两个已公开 CVE 的修复版只发布在其自建源。改用维护活跃的 `read-excel-file`，代价是不支持老式 `.xls` |
| **计算全放浏览器，Node 只做 LLM 代理** | Vercel 有 4.5 MB 请求体限制；且「数据不出浏览器」是产品的核心承诺，也是隐私叙事的基础 |
| **`core/` 是平台无关的纯 TS** | 浏览器 Web Worker 与将来的 MCP Server 共用同一份实现，从架构上杜绝「界面显示的结果」与「导出脚本的结果」不一致 |
| **工具刻意不带 `execute`** | AI SDK 里没有 `execute` 的工具会终止本轮循环、把调用交给客户端 —— 这是「工具在浏览器执行、原始数据不出本机」能成立的**技术前提**。有测试锁死这一条 |
| **阶段从消息派生，不另存状态** | 消息的 parts 序列本身就编码了阶段流转；再存一份就必须靠 effect 同步，同步迟早会漏。因此删掉了 Task 5 写的显式流转函数（`nextPhase` 等，零生产调用方）—— 一份只存在于代码里、界面并不使用的状态机，给不了可控性，只会给一种「我们有状态机」的错觉。**答辩被问「你的状态机在哪」时按这个答** |
| **不删「取值分布」里的原始写法** | 类别归并必须看得见「硕士 / 研究生 / 硕士研究生」的差异，抹掉这个功能就不成立。脱敏保护的是**样例**，不是分布 —— 这条边界由测试固化 |
| **一次提交一条问题，不提交整份报告** | 真模型实测：整份报告作为一次工具调用的载荷会流不完，用户拿不到任何结论。可靠性边界压倒了「一次说完」的简洁 |
| **E2E 默认 mock、真实调用单独一条默认跳过** | 真实调用会花钱，而且网络抖动会让门禁随机变红 —— 到时候分不清是「代码坏了」还是「网断了」，门禁就失去判断力 |
| **知识库与 Plan 3 走并行轨道，不串行等** | Plan 3 只有 RAG 的**内容效果**依赖团队填的东西；检索管线本身、端侧 embedding、清洗执行、脚本导出都不依赖。团队填 50 条可能要一两周，串行等就是白等工期。**做法**：我用格式规格 + 现有 17 条通用条目把管线开发完并测好，团队的内容分批进来就自动变强（`knowledge/README.md` §10 也写明了「不需要一次写完」） |
| **条目结构要在批量填之前冻结** | `knowledge/schema.md` 的 11 列是我**设计**出来的，没经过真实填写检验。请团队**先填 3–5 条**，确认「填得下去、字段够用、不别扭」—— 现在改成本最低；等填了 50 条再改就要全部返工。这也和上面那条并行轨道配套：结构一冻结，两条轨道就能同时推进 |
