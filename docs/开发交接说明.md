## 二、这台机器的特殊情况（重要）

这些在通用文档里查不到，但不知道就会卡住。

| 事项 | 说明 |
| --- | --- |
| **C 盘空间紧张** | 只剩约 30 GB，所有安装必须落 D 盘。执行 pnpm 前先设 `$env:TEMP='D:\tmp'; $env:TMP='D:\tmp'` |
| **Playwright 浏览器在 D 盘** | 跑端到端测试前设 `$env:PLAYWRIGHT_BROWSERS_PATH='D:\ms-playwright'`，否则会报找不到浏览器 |
| **git 用了 schannel 后端** | `D:\git\Git\etc\gitconfig` 里 `sslBackend = schannel`。原来的 openssl 因 CA 证书包过期连不上 GitHub。备份在同目录 `.bak-*` |
| **pnpm 12 会报 ERR_PNPM_IGNORED_BUILDS** | **可以忽略**。那是 pnpm 拦截 postinstall 的安全策略，本项目依赖的平台二进制走 optionalDependencies，不受影响 |
| **npm 全局目录在 C 盘** | `npm install -g` 会装到 C 盘。需要全局 CLI 时用 `pnpm` 或直接 `npx` |
| **PowerShell 执行策略** | `.ps1` 脚本可能被拦（如 `tsc.ps1`）。改用 `.cmd` 版本，例如 `node_modules/.bin/tsc.cmd` |
| **门禁脚本的坑** | 不要写 `pnpm test 2>&1 \| Select-Object -First N` —— PowerShell 会提前关闭管道并掐断 pnpm，把通过的测试记成失败。先存变量再过滤 |
| **`next-env.d.ts` 会来回抖** | 跑 `pnpm build` 与 `pnpm dev` 会让它在 `.next/types/` 与 `.next/dev/types/` 之间切换。那是 Next 自动生成的，**不要提交它**，每次还原掉即可（`git checkout -- next-env.d.ts`） |
| **dev server 会锁住源码文件** | 开着 `pnpm dev` 时改 `src/` 下的文件，可能报 `ReplaceFileW EIO (Win32 1175)`。那是 Turbopack 的文件监听持有句柄，**不是磁盘坏了**。先停 dev server 再改，或重试一次 |
| **别用 shell 改源码** | `Get-Content -Raw` 读 UTF-8 文件会按本机 ANSI（GBK）解码，再 `Set-Content` 写回就把中文全弄乱、引号还会变成 `?`，文件语法直接崩。改代码只用编辑工具 |
| **临时产物别放进 `test-results/`** | Playwright 每次跑测试都会清空自己的输出目录，放在那里的截图之类会被无声删掉 |
| **读 UTF-8 文件时控制台可能乱码** | `Get-Content`/`Select-String` 输出中文乱码通常只是控制台编码问题，不是文件坏了。用读取工具确认，或先 `[Console]::OutputEncoding=[System.Text.Encoding]::UTF8` |

## 三、开发流程约定

前两个计划都是这样走的，建议延续。

### 每个计划走一遍

```
1. 写计划      → docs/superpowers/plans/YYYY-MM-DD-<名字>.md
                 每个任务按 TDD 组织：写失败测试 → 确认失败 → 实现 → 确认通过 → 提交
2. 建特性分支  → git checkout -b feat/<名字>
3. 逐任务执行  → 每任务结束跑门禁，通过才提交
4. 整分支审查  → 派一个全新上下文的审查者，只读检查整条分支
5. 修复         → Critical 与 Important 一次修完，每条都要有先失败后通过的测试
6. 合并         → git merge --no-ff，在合并结果上重新跑门禁，然后删分支
```

对应的 skill：`writing-plans` → `executing-plans` → `requesting-code-review` → `finishing-a-development-branch`。

### 提交前的四道门禁

```powershell
$env:TEMP='D:\tmp'; $env:TMP='D:\tmp'
$env:PLAYWRIGHT_BROWSERS_PATH='D:\ms-playwright'

& node_modules/.bin/tsc.cmd --noEmit   # 类型
pnpm test                              # 单元测试
pnpm test:e2e                          # 端到端（含 .tsx 改动时）
pnpm build                             # 构建
```

**typecheck 必须当门禁**。Plan 1b 执行时有一次把 typecheck 和 commit 放在同一段脚本却没拿它做判断，结果一个类型错误被提交进去了。

### 合并用 `--no-ff`

比赛要求「保留完整 Git 提交历史，体现真实的开发过程」。合并提交让历史读起来是「功能分支 → 审查 → 合并」，而不是一堆平铺的 `update`。

## 四、写作与代码约定

| 项 | 约定 |

### 8.3.3 本轮会话（10-13）做了什么：知识库构建管线

目标是 §8.3.2 末尾那件「现在就能做」的活：把 `knowledge/知识库模板.xlsx` 转成

**新建**

| 文件 | 作用 |
| --- | --- |
| `knowledge/tools/build-index.py` | xlsx → 校验 → `entries/*.yaml` → `index/rules.json` + 报告。含 39 项内嵌自测 |

**生成**：`knowledge/entries/general.yaml`（17 条）、`knowledge/index/rules.json`。

**两条要记住的判断**

1. **向量后端要有一个离线降级路径。** `schema.md` 要求向量在构建期算好，但构建不该依赖
   网络与 200MB 模型下载。所以默认后端是 `char-ngram-hash`（哈希 2-gram 词袋 + L2 归一化，
   用 blake2b 保证跨进程确定）。它产出的是**真向量**但不是**语义**模型，`model` 字段如实
   写出来，不冒名 bge。要真语义就 `--embedder bge`，届时**阈值必须重扫**（阈值与模型强绑定）。
   ——这与产品其它部分的处理方式一致（端侧 embedding 不可用 → 降级结构化规则）。

2. **规格里的判据落到代码时要收窄，否则假警报会把真信号淹掉。** 三处：
   裸匹配「略」会命中「策略／忽略」；「非三个已知 sheet 即报错」会打中模板自带的
   两张文档性 sheet；「`适用字段` 留空即警告」会给 8 条合法的泛化规则各出一条噪音。
   三处都收窄了，理由写在 `schema.md` 第 3 节。

**一个真实发现**：字段别名聚类把 `general-gb-code-standards` 暴露出来了 —— 它一条声明了
`性别／学历／民族／行政区划／专业／行业` 7 个别名，跨了多个字段族，正是 README 第 7 节
点名的反模式。脚本只提出疑问、不下结论（`学号／工号／编号` 是同族，靠字符 2-gram
分不出它和 `性别／学历` 的区别），判定权交回填表的人。

**Python 工具链跑不进 Vitest**，所以测试内嵌成 `build-index.py --self-test`
（39 项断言，覆盖全部错误判据的正反例、空行跳过、YAML 往返保内容、向量确定性与归一化、
2-gram 跨空白、`rules.json` 回读自检）。**改动该脚本后必须跑它**，这条已写进 `schema.md`。

**两条产物自证**（都不靠人眼）：`entries/*.yaml` 写完重载比对每个字段（块标量可能悄悄改内容），
`index/rules.json` 写完回读校验条目数／向量维度／归一化／正文非空。没通过的 `rules.json`
会被当场删掉 —— 半份坏索引比没有索引更难查。

**门禁结果**：`--self-test` 39/39 通过；`--check` 与完整构建 exit 0；17 条 0 错误 8 警告；
自召回 Hit@1 0.8824、Hit@5 1.0、MRR 0.9412。`src/` 一行未动，所以四道门禁不受影响。

### 8.4 会话里做出、但没写进代码的决定

| 决定 | 理由 |
| --- | --- |
| **侧边栏「结构抄抖音、风格不抄」** | 分组/图标/选中态的信息架构是标准的，该学；但深色背景+大图标+高饱和色是消费级内容 App 的语汇，用在科研数据工具上传递的信息是错的。评分表里「交互模式创新 7%」考的是交互方式是否超越传统，不是长得像哪个热门 App |
| **未实现的功能要留在界面上（禁用+标注）** | 直接不渲染会让人以为产品就这几个功能；只置灰不解释会让人反复点击 |
| **不用组件库 CLI** | shadcn 本质是复制源码进项目，我们只需要几个简单组件；引入会连带一套主题与几十个 CSS 变量，且其 registry 在境内访问慢。复杂交互后续直接用 Radix 原语 |
| **不用 SheetJS（`xlsx`）** | npm 上的版本停在 0.18.5，两个已公开 CVE 的修复版只发布在其自建源。改用维护活跃的 `read-excel-file`，代价是不支持老式 `.xls` |
| **计算全放浏览器，Node 只做 LLM 代理** | Vercel 有 4.5 MB 请求体限制；且「数据不出浏览器」是产品的核心承诺，也是隐私叙事的基础 |
| **`core/` 是平台无关的纯 TS** | 浏览器 Web Worker 与将来的 MCP Server 共用同一份实现，从架构上杜绝「界面显示的结果」与「导出脚本的结果」不一致 |
| **工具刻意不带 `execute`** | AI SDK 里没有 `execute` 的工具会终止本轮循环、把调用交给客户端 —— 这是「工具在浏览器执行、原始数据不出本机」能成立的**技术前提**。有测试锁死这一条 |
| **阶段从消息派生，不另存状态** | 消息的 parts 序列本身就编码了阶段流转；再存一份就必须靠 effect 同步，同步迟早会漏。因此删掉了 Task 5 写的显式流转函数（`nextPhase` 等，零生产调用方）—— 一份只存在于代码里、界面并不使用的状态机，给不了可控性，只会给一种「我们有状态机」的错觉。**答辩被问「你的状态机在哪」时按这个答** |
| **不删「取值分布」里的原始写法** | 类别归并必须看得见「硕士 / 研究生 / 硕士研究生」的差异，抹掉这个功能就不成立。脱敏保护的是**样例**，不是分布 —— 这条边界由测试固化 |
| **一次提交一条问题，不提交整份报告** | 真模型实测：整份报告作为一次工具调用的载荷会流不完，用户拿不到任何结论。可靠性边界压倒了「一次说完」的简洁 |
| **E2E 默认 mock、真实调用单独一条默认跳过** | 真实调用会花钱，而且网络抖动会让门禁随机变红 —— 到时候分不清是「代码坏了」还是「网断了」，门禁就失去判断力 |

2. **L2 字面层自动归并反义/否定类取值** —— `semanticHigh = ∞` 关掉了语义路的自动归并，

另有一条 **Critical 是我自己上一轮的判断错了**：我在 ledger 里写过「出站面没有绕过白名单的

### 一条「以为是产品 bug、其实是自己的 mock 在说谎」的教训

**先给结论**：产品**没有**「第二次分析撞消息 id」这个问题。它是我自己的 mock
不忠实造成的假象 —— 而我在 §8.9 的第一版里已经把它写成「用真实接口验过、仍未修」，
**那是错的记录**，这里改回来。

**被误判的两次现象**：

| 看到的现象 | 当时的结论 | 真相 |
| --- | --- | --- |
| 真实接口返回 `data: {"type":"start","messageId":"<上一条助手消息 id>"}` | 「服务端复用了旧 id，是 bug」 | 这是 SDK 的**设计**：续轮复用上一条助手消息的 id，客户端才能把它归并回同一条消息。一轮分析内部始终一条消息，正是我们要的 |
| DOM 里出现两条 id 相同的助手消息 + React 报重复 key | 「第二次分析会撞 id」 | mock **一律**回 `msg-1`。第二轮客户端本来会自己生成新 id，是 mock 硬把旧 id 塞回去的 —— 真服务端在「历史以 user 结尾」时**根本不带 messageId**，客户端自己发号 |

**真实服务端的 id 规则**（对着接口实测，不是读代码猜的）：

```
历史以 user 结尾      → data: {"type":"start"}                        （不带 messageId，客户端自己生成）
历史以 assistant 结尾 → data: {"type":"start","messageId":"<上一条助手消息 id>"}（续轮归并回同一条消息）
```

**查证过程本身值得记**（因为差一步就会去改产品代码）：

1. 先想「服务端每轮发新 id」→ 给 route 传了 `generateMessageId: generateId`
2. 写测试断言「不得等于上一条助手消息的 id」→ **测试立刻失败**，说明这个选项**是空转**
3. 去读 SDK：`handleUIMessageStreamFinish` 在「最后一条是助手消息」时**无条件覆盖**
   `messageId = lastMessage.id`（`dist/index.js:7127`）—— 选项根本到不了生效点
4. 于是撤回产品改动，转而问「那客户端为什么不撞」→ 用**忠实复刻服务端规则**的 mock
   在浏览器里连做两轮分析：每轮各一条助手消息，id 各不相同，控制台干净

**留下的东西**：`tests/e2e/plan-and-rules.spec.ts` 里的 `serverStartChunk()` 复刻了上面那条
真实规则（注释里写着出处），`src/app/api/agent/route.ts` 留了一段说明「为什么刻意不传
`generateMessageId`」。产品代码一行没改。

**要记住的教训**：mock 在**协议层**撒谎，比 mock 少写一个用例危险得多 —— 它会让
「根本不存在的问题」看起来有真实接口的铁证，还会带着人删掉正确的行为。
判据是：**这条现象换成真服务端会不会出现？** 我当初的验证只到了「服务端确实回旧 id」
（真的），却没有再问一句「客户端对这个 id 本来期望什么」（那才是关键）。

### mock 的档位顺序（缺一档就无限续跑）

同一次排查里又撞上一次无限续跑：mock 少写了「计划已被执行」这一档，客户端收到同样的
`plan_checks` 就再执行一次，助手消息堆到 474 个 part。四档顺序即优先级：

1. 计划已执行（请求体里出现 `"tool-plan_checks"`）→ 说结论
2. 用户又问了第二轮（会话里出现第 2 个 `<数据集摘要>`）→ 重新提计划
3. 用户点了「按此计划执行」→ 执行检查
4. 首轮 → 提计划

**判据不能用工具名单独判断**：`tool-plan_checks` 在「按此计划执行」那条消息上行时依然
留在会话历史里，用它当判据会把续轮判成首轮。

**顺带记一句**：本轮全量 E2E 出现过一次未定位的失败（未留住失败段落），重跑多次未复现。
与 §8.5 第 7 条（单测偶发失败）同一个态度：没看到真实失败之前不加 retry、不放宽断言。
**这一条已在 §8.10 定位并修掉** —— 不是偶发，是 E2E 在依赖 huggingface.co 的连通性。

### `literal` 阈值：一条欠账牵出一个 spec 违反

§8.8 只说了「0.86 未经扫描」。扫完发现比记载的更严重 —— 它是**硬指标不达标**：

| 点 | 阈值 | Precision | Recall | F0.5 |
| --- | --- | --- | --- | --- |
| 旧值（未扫过） | 0.86 | **0.8222** | 0.3458 | 0.6446 |
| 归并阈值（现用） | **0.95** | **1.0000** | 0.0561 | 0.2290 |
| 待确认下界（现用） | **0.84** | 0.8036 | 0.4206 | **0.6798** |

spec §5.5.4 要求「Precision@建议阈值 **≥ 0.95**」并给了方法（扫 `[0.50,0.99]`，
取达标点中 Recall 最大的）。0.86 处只有 0.8222 —— **不达标**。

而只看达标点召回只剩 0.056（一百对同义写法只提起五对）。所以补一条
**待确认下界**，与 L3 的处理同构（`semanticHigh` 不可达 + `semanticLow` 待确认）：
**待确认档不自动改数据**，只把候选列给用户核对，因此允许精度低得多。
取 F0.5 最优（0.84）而不是召回最大（0.67），因为 spec 定的策略是 Precision 优先，
而 F0.5 正是把精度权重放大 5 倍的那个形式化。

**顺带拆开了一处混说**：待确认原先只有一条路径、文案统一写成「语义相近」。
现在 L2 与 L3 的待确认**分成两条**，文案、证据字段与置信度都不同
（L2 是「写法相近」0.6，L3 是「语义相近」0.45）—— 依据来自哪一层必须说清，
否则语义模型会领到不属于它的功劳。

曲线的产出者是 `src/core/synonyms/literal-scan.test.ts`：它**直接 import
生产的 `literalSimilarity` 与 `isGuardedPair`**，所以不存在「抄错一份算法」的可能
（这也正是没有把它写成独立脚本的原因：项目的 TS 无法被 Node 直接 import，
而任何脚本化的尝试都得再抄一份实现）。报告见
`knowledge/reports/embedding-validation.md` 附录 A。

### `subject` 从「死参数」到「可选加权」

`retrieveRules` 原先的语义是「不传 subject 就只召回通用条目」—— 而运行时
**没有任何一处会传它**（也没有地方能知道数据集属于哪个学科），于是索引里的学科层
（真实索引 21 条 / 18.6%）结构上永远够不着。

改成「学科只加权、不排除」之后，同一组查询的排序变化（`retrieve.test.ts` 与
下面的实测都钉着）：

| 查询 | 变化 |
| --- | --- |
| `绩点 3.5 4.0 2.8` | 第 1 位变成 `ds-gpa-scale-caliber` |
| `学期 2023-2024-1 …` | 第 1 位变成 `ds-term-year-encoding` |
| `成绩 85 90 缺考` | 前 4 位全是学科条目（含 `ds-grade-marker-special`，正对「缺考」） |
| `学历 …` | 学科条目 `general-gb-education-code` 进前 5 |

代价是「备注」这类通用查询可能串进一条学科条目（实测 1 条）。这是可接受的：
**学科条目本来就该在相关的查询里出现**，而通用条目没有被降权。

### `core → agent` 的契约搬运

搬运时特意多做了一件事：**把 Zod schema 钉在搬过去的类型上**。

export const _cleaningActionShape = cleaningActionSchema satisfies z.ZodType<CleaningAction>;

门禁那一半也补上了（之前是**有意的半成品**：契约不搬就没法守）。并且**验证过它会红**：
往 `core/numeric.ts` 插一条 `import type { Issue } from '@/agent/shared/schemas'`，
`platform.test.ts` 立刻失败并指出是哪个文件、哪条规则。**一条没验证过会响的门禁，
和没有门禁是一回事。**

修完连跑 3 次：**53 passed / 1 skipped，噪音 0，三次一致**。
要验证真实模型加载时，不调用这个 helper 即可（那时接受它依赖网络）。

### 有意不改的一条

**单位检查不认千分位**（`1,000 mg` 会被 `parseValue` 的正则跳过）。这不是 bug 而是
已知局限：那条正则是刻意收紧的，注释写明「解析越宽松，误报越多，而这条检查的误报
会让用户去改本来正确的数据」。千分位是**格式**问题而不是单位问题，为一个召回率缺口
去放宽容错，换来的是用户对整条检查的信任下降。**留着并写进已知局限，比改它更对。**

写这份数据时踩到并写进注释/README 的四个坑：

| 坑 | 表现 |
| --- | --- |
| **答案粒度必须跟着检查粒度走** | `missing` 是列级问题、不给 `rowIndices`，而答案起初按单元格记了 200 条并强制匹配行号 → 测出「200 处漏报」，漏的是口径 |

| **一处数据可能被两项检查各报一次** | 年龄 999 同时命中 `outliers` 与 `range-rules`；剂量带单位的 4 行同时命中 `unit-consistency` 与 `type-consistency`。评分时不能算成两次独立命中 |

取值生效，而 `type-consistency` 只在列被判成 `mixed` 时工作，**日期合法性当前没实现**。
评测集记录能力边界和记录能力一样重要，否则「评测通过」会被读成「这类问题我们都查得出来」。

### Task 4：L5 系统评测（已完成）

按 spec §2.3 的基准（**5 万行 × 50 列，剖析 ≤3 秒、全流程 ≤30 秒**）实测，
5 次取中位数并附最小/最大作抖动证据。数据集是最坏形态（四分之一列逐行唯一文本）。

| 场景 | 中位数 | 预算 | 结论 |
| --- | --- | --- | --- |
| 剖析 5 万 × 50 | **1108 ms** | 3000 ms | ✅ 2.7 倍余量 |
| 全量检查 5 万 × 50 | **3232 ms** | 30000 ms | ✅ 9.3 倍余量 |
| 类别归并 500 唯一值 × 3 列（2000 行） | **1178 ms** | —— | 占全量检查约 36% |

**三条给后续任务用的结论**：

1. 两项预算都达标且余量很大 —— 剖析与全量检查**都不是**性能瓶颈
2. **类别归并的耗时与行数无关、只看唯一值数**：2000 行 × 3 列（各 500 唯一值）就要
   1178 ms。这解释了 `MAX_UNIQUE_VALUES = 500` 的由来 —— 放开到 2000 个唯一值是
   平方增长（约 200 万对 → 十秒级），会吃掉 30 秒预算
3. **Task 8（Worker 化）的定位是「体验」而不是「指标不达标」**。实测 3.2 秒远在预算内，
   所以不能说「为了不超时」；成立的理由只有一条 —— 3.2 秒的同步计算会把主线程冻住，
   而 spec §2.3 要求「界面全程不卡顿」。**报告里如实这么写**，免得 Task 8 被包装成
   「性能不达标所以必须做」

**token 与成本（估算，不是实测）**：5 万 × 50 的摘要只有 **8099 字符 ≈ 2674 输入 token**，
单次分析约 **¥0.0213**（单价硬编码为 DeepSeek 公开定价量级并注明换模型须改此处）。
摘要规模与数据规模基本脱钩 —— 这是「结构摘要」机制在成本侧的收益。

**一个要留意的代价**：本文件独占 **36 秒**（3 个场景 × 5 次采样 × 5 万行），
把全量单测从 4.4 秒推到 **38 秒**。这是 spec 预算基准的代价；
若日后觉得拖慢开发循环，可把 5 万那一档减到 3 次采样或移出默认套件。

### Task 5：L4 Agent 层评测（已完成，真调模型）

**隔离策略**：不进日常门禁（`pnpm test` 会跳过），只有 `pnpm eval:agent` 才跑
（靠 `RUN_AGENT_EVAL` 环境变量开启；`package.json` 里用 `node -e` 设变量再 spawn，
跨平台且不加依赖 —— `VAR=1 cmd` 只在 bash 成立）。

**脚本要自己扮演浏览器**：工具在浏览器执行（AI SDK 客户端工具不带 `execute`），
所以它显式用**生产的 `executeToolCall`** 执行再回填 `tool-<name>` part。

| 指标 | 值 | 口径 |
| --- | --- | --- |
| 工具调用正确率 | 100%（12/12） | 只看「工具**被调用过**」 |
| **工具成功率** | **95.7%**（112/117） | 返回 `ok`。**这一行才反映能力** |
| 平均轮次 | 7.17（2–12） | 一轮 = 一次 POST |
| **被轮次上限截断** | **6/12** | 最后一轮仍有工具调用 = 没跑完 |
| 失败恢复率 | 100%（5/5） | 失败后仍继续推进 |
| 计划格式有效 | 9/10 | **这不是「计划合理」** |

**三条结论**：

1. **一半的运行没跑完** —— `defects` 三次全部撞到 12 轮上限。
   **第一次跑时这个数字被掩盖了**：当时上限是 8、三次都恰好 8 轮，看起来像
   「稳定完成」。加了 `hitRoundLimit` 标记才看出那是**每次都在上限处被截断**。
   教训：指标必须区分「自然结束」与「被截断」，否则截断会被读成一致性。
2. **同一条查询产出不稳定** —— `defects` 三次提交 4/7/8 条；`rule-lookup` 前两次
   2 轮答完、第三次跑成 9 轮提交 5 条。说明**没有收敛判据**：模型不知道「够」在哪。
3. **越界请求的拒绝合格** —— 问「相关系数矩阵 + 多元回归」时三次都明确说做不到
   并说明原因，把话题拉回数据质量（产品明文不做统计建模，spec §2.4）。

### 这一轮修掉的两处**评测失真**（比任务本身更值得记）

第一次真跑之后核对原始记录，发现两个问题 —— 两个都会让报告「好看但没效」：

| 失真 | 表现 | 为什么危险 |
| --- | --- | --- |
| `query_rules` **全部失败**（23 次） | `loadRuleIndex()` 里是相对 URL `fetch('/knowledge/rules.json')`，Node 直接抛 `Failed to parse URL` | 「工具调用正确率」量的是「调了没有」，**规则检索那一路根本没被评到**。这是最坏的一种失真：数字满分，被测能力其实没跑。已补 fetch 补丁（优先读本地 `public/` 副本） |
| 缺**截断标记** | `defects` 三次都恰好 8 轮 | 会被写成「稳定完成」，而真相是「每次都被上限打断」。已加 `hitRoundLimit`，并在指标表里单列一行 |

**还发现一条真 bug 的实证**：模型编造了 `checkId = "describe-剂量"`，被**生产的
执行器**拦下。这也是「用生产执行器而不是另写一份」的实证 —— 另写一份的话，
这个编造值会被静默接受。

**如实写明未测的**：**真实 token 用量拿不到** —— `/api/agent` 的 SSE 流里
`finish` 块只有 `finishReason`、不带 `usage`（真跑时验证过）。要拿到得改产品出站协议，
为评测改产品不划算。样本量 3 次也不足以谈分布：`[4,7,8]` 只能说「不稳定」，
**不能给方差或置信区间**。

报告最后一节写了「下一步该做什么」：给 Agent 一个**收敛判据**（系统指令里写明
「查够就该收尾」，或重新权衡 `submit_issue` 的批量入口）。
在那之前，「平均轮次」与「提交条数」**不适合**写进技术文档当成绩 ——
它们现在量的是「模型想查多久」，不是「产品有多能干」。

### Task 6：指标看板（挂 `/export`，已完成）

四层评测的数字第一次进界面。看板回答三个问题，而不是「把数字排开」：

1. **这份数据有多脏** —— 本次分析的规模/检出/高优先级/按检查项分布
2. **系统判断得准不准** —— 各层评测，**每个指标都带判据与达标线**
3. **这次分析做了什么** —— 同义归并状态、留痕步数、检查项

第 2 点里「带判据」是关键：看板最容易退化成一排漂亮的数字，而**没有判据的
数字读不出好坏** —— 「Precision 93.3%」可以是优秀也可以是灾难，取决于要求。
所以 `EvalMetric.rule` 是必填字段，E2E 也直接断言「达标/未达标」与判据文案。

**架构上的两个决定**：

| 决定 | 理由 |

### Task 8：把检查搬进 Worker

- `src/worker/checks.worker.ts` 是**薄壳，零检查逻辑** —— 唯一的计算是 `runAllChecks`，
  与主线程同一份 core。这是 Review Focus 第 6 条的落实：一旦这里出现第二份实现，
  「界面显示的结果」会与「导出脚本 / MCP Server 的结果」慢慢分叉，而分叉不会有任何报错。
- 等价性先于性能：`workerChecks.test.ts` 直接断言 Worker 端输出与主线程 `runAllChecks`
  **逐字段一致（id 除外）**，并且用一个**真的调处理函数**的假 Worker，而不是返回固定值的桩。
- 客户端的超时 / `error` 事件 / 构造失败 / 只降级一次四个模式照抄 `parser/workerClient.ts`
  —— 那里已经把三种失败都踩过一遍，不重新设计。
- 一个计划外的判断：`extraChecks` 里是**函数**，过不了结构化克隆。这种情况直接在主线程跑
  并告警。悄悄换实现会让「Worker 里跑的就是同一份 core」这条承诺出现看不见的裂缝。
- 界面新增「正在检查」态（`checksStatus` / `checksNote`）。**空的问题清单在界面上的意思是
  「这份数据干净」，而检查没跑完时说这句话就是在给一个我们并不知道的结论** ——
  它听起来还像好消息。检查失败同理，说的是「清单是空的，但不代表没问题」。
- **E2E 守的是「Worker 真的生效了」**：降级路径的结果与 Worker 路径一模一样，所以断言结果
  无法证明 Worker 在用。`worker-checks.spec.ts` 改断言**控制台里没有 `[checks]` 降级警告**。
  这是本轮最值得记的一条测试设计经验：一条「两条路结果相同」的实现，必须有测试盯住**走的是哪条路**。

**定位：这是体验优化，不是「性能不达标」。** 5 万 × 50 全量检查约 3.2 秒、预算 30 秒，
远没超。成立的理由只有一条：数秒同步计算会把主线程冻住，而 spec §2.3 要求「界面全程不卡顿」。

**实测（同一台机器、同一次运行）**，已写进 `knowledge/reports/eval-system.md`：

| 阶段 | 中位数 |
| --- | --- |
| Worker 化之前，主线程同步阻塞 | **4095 ms**（剖析 927 + 检查 3168） |
| └ 剖析（**仍在主线程**） | 927 ms |
| └ 结构化克隆（搬走检查后**新增**） | 92 ms |
| └ 检查（已移出主线程） | 0 ms |
| Worker 化之后，主线程同步阻塞 | **1019 ms**（约降 4 倍） |

**如实说三件事**（答辩会被问到，别把话说满）：

1. **不是「不卡了」，是「卡得少了」。** 最坏用例下主线程仍有约 1 秒同步开销，其中 927 ms 是剖析。
   把 Task 8 写成「界面全程不卡顿已达成」是超额声明。
2. **搬走也有新成本。** 结构化克隆 92 ms 是新增的、同步的；「搬进 Worker 会更快」不成立，
   总耗时基本不变，还多了一次复制。收益是**那 3 秒不再落在主线程上**。
3. **口径**：Node 的 `structuredClone` 与浏览器 `postMessage` 用同一套克隆算法，但不等于
   真实 postMessage 的完整成本（后者还有跨线程投递）。这个数只回答数量级。

### Task 9：零散欠账

**修 `read_csv` 把 `'001'` 推成 `1`。** 生成的 pandas 脚本原来用 `pd.read_csv(SOURCE, encoding="utf-8-sig")`，
pandas 的类型推断会把 `001` 读成 `1` —— 学号、编号、行政区划码这类字段的前导零就没了，
于是「脚本跑出来的结果」与「界面上看到的结果」不一致，直接违背「脚本是真跑过的」那条承诺。

修法是**只给确实会被改写的列加 `dtype`**，不一刀切 `dtype=str`：

```python
df = pd.read_csv(SOURCE, encoding="utf-8-sig", dtype={'学号': str})
```

判据是「文本形式与数值形式不同」（`String(Number(v)) !== v`），而不是「看起来像数字」：
`'5'` 读成 5 写回还是 `'5'`，不必干预（硬加 dtype 反而改变比较与空值行为）；
`'001'`、`'5.50'`、`' 5 '` 才会被改写。6 条测试钉住正反两个方向。

**顺带做了一次语法校验**：用 `python -m py_compile` 验了含单引号列名、含空格文件名、
两种清洗动作的生成脚本，**通过**。这条校验没进回归（要 python 环境），已登记为欠账。

### 坑 1：`*.vercel.app` 在境内被阻断（部署成功 ≠ 评委能打开）

Vercel 分到的域名 `ai-web.xxxx.vercel.app` 在本机实测：TLS 握手被重置 / 超时；同机的 `vercel.com`
后台却能打开。这是域名级阻断，不是配置问题。

**解法**：绑自有域名。`*.vercel.app` 被墙不代表自定义域名被墙 —— 实测 `https://www.ai-web.me`
从境内直连 200。**这一步必须在演示前做，否则「可访问的演示地址」不成立。**

### 坑 2：换平台不是白捡（Zeabur 已对新项目收费）

试过 Zeabur 做备用：新项目必须先买服务器（最便宜 Tencent US$3/月起），免费档不再对新用户开放。
**放弃**，走「自定义域名 + Vercel」。顺带否掉了 Cloudflare Pages（Next 16 + SSE 要走 OpenNext 适配，
临期不值得）。

### 坑 3：第三方镜像在**真实浏览器里**不可用（CORS 这件事不能用 curl 验）

原先语义模型从 `hf-mirror.com` 拉。curl 看响应头**一切正常**（GET 与 OPTIONS 预检都回
`Access-Control-Allow-Origin`），但**真实浏览器 `fetch` 直接 `Failed to fetch`**，控制台写着
`blocked by CORS policy`。于是线上语义归并永远降级 —— 界面会诚实提示「本次没有被检查」，
但「硕士／研究生」这个招牌演示点就没了。

**解法：模型自托管**（`scripts/fetch-model.mjs`，prebuild 时下到 `public/models/`，23.4 MB，
产物 gitignore）。`allowLocalModels` 在浏览器默认是 **false**，必须显式打开。

**教训**：验证第三方资源可用性时必须用**浏览器**，curl 的头只能证明「服务器愿意给」，
证明不了「浏览器愿意收」。

### 坑 4：模型本地了，推理运行时还在从 jsDelivr 拉

模型改成同源后仍然降级，控制台里换了一条 URL：
`https://cdn.jsdelivr.net/npm/onnxruntime-web@.../ort-wasm-simd-threaded.asyncify.wasm`
—— 跑模型的 **WASM 运行时**默认从 CDN 拉，而 jsDelivr 在境内常被阻断。

**解法**：`scripts/sync-ort-wasm.mjs` 把 `node_modules/onnxruntime-web/dist/` 里的
两个变体（`asyncify` = WASM 后端、`jsep` = WebGPU 后端）拷到 `public/ort/`（52.8 MB，
产物 gitignore），`loadModel.ts` 里 `env.backends.onnx.wasm.wasmPaths = '/ort/'`。

### 坑 4 的连带发现：`pipeline()` 会缓存失败的加载 Promise

原代码是「先试 webgpu，失败再试 wasm」。实测在无显卡环境（headless/CI/虚拟机）**永远失败**：
transformers.js 的 `pipeline()` 按模型 id 缓存**加载 Promise**，第一次（webgpu）失败后，
第二次（wasm）拿回的是同一个已失败的 Promise，报错文案里仍然写着 `[webgpu]`。

**解法：回退必须发生在加载之前** —— 先 `navigator.gpu.requestAdapter()` 探测有没有真实适配器，
再**只用选中的后端加载一次**（`pickDevice()`）。这比「只看 `navigator.gpu` 是否存在」准一档。

### 部署相关的三条维护须知

1. **构建需要一次网络下载**（模型 23 MB，`prebuild` 跑）。失败**不拦构建**，应用会降级并在界面明说；
   换机器/换平台时先确认能连通 `huggingface.co` 或 `hf-mirror.com`
2. **`NEXT_PUBLIC_HF_MIRROR` 已经不再需要**（代码里那一行已删）。Vercel 上留着无害，但别以为它在起作用
3. **部署包体积**：`public/models` 23 MB + `public/ort` 53 MB（都是构建产物、不入库）。若平台报体积超限，
   可以先只留 `asyncify`（WASM 后端），牺牲 WebGPU 加速换部署包瘦一半

### 8.14.1 本地/远端分叉对齐（提交 `170a8ba` + `4d584bc`）

**背景**：远端 `main = f86f2c2` 与本地 `HEAD = 6d29018` 内容等价，但 git 历史是兄弟提交
—— 4 份 md（`技术文档.md` / `开发交接说明.md` / `交接-2026-10-21.md` / `交接-2026-10-23-界面方案第一轮.md`）
在远端以 CRLF 存储、本地为 LF。上一轮用 REST API 直接推过内容，于是同一个内容有了两个提交号。

**做法**（在远端 tip 之上继续开发，不 force push）：

1. 用 GitHub API 取远端 commit/tree，把 4 个 CRLF blob 下载并 `git hash-object -w --no-filters`
   写进本地对象库（**必须 `--no-filters`**，否则 `core.autocrlf` 会把 CRLF 再转回 LF，哈希对不上）；
2. 以本地 `6d29018` 的树为底替换这 4 个 blob，`write-tree` 重建出远端 tree，再用相同
   author/committer/日期重建 commit 对象，**SHA 校验等于 `f86f2c2`** 后才继续；
3. 以 `f86f2c2` 为父提交「统一 4 份 md 行尾为 LF」，再提交 10-25 交接文档，直接 `git push`
   （远端 tip 是父提交，属 fast-forward，不需要 force）；
4. 本地 `main`、`origin/main`、远端三者一致；旧提交保留在本地分支 `backup/main-6d29018`。

**两条环境经验**：
- `api.github.com` 的 TCP 建连在这台机器上常超过 10 秒，Node 内置 `fetch` 默认 10 秒会报
  `fetch failed`（同一时刻 curl / `Invoke-RestMethod` 是通的）。改用 `node:https` 显式放大
  连接超时并重试，或先设 `--dns-result-order=ipv4first`。
- 用 REST API 重建本地提交时，**远端提交 SHA 与本地不保证一致**（服务端对消息结尾换行、
  日期时区的序列化与本地 git 不完全相同）。能 `git fetch` / `git push` 时优先走 git。

## 8.16 本轮会话（2026-10-25 下半场之二）：检查覆盖地图

**要解决的问题**：问题清单只说明「报了什么」，不能说明「查了什么」。空清单在用户眼里
很容易被读成「全部检查通过」，而值域规则没配置、语义模型降级、某个检查项崩了，
都会让空清单显得比实际更干净。这一轮把「这份数据到底检查到什么程度」做成一张表。

### 8.16.1 做了什么

- 质量检查页新增 **「检查覆盖地图」**（`src/ui/components/CoverageMap.tsx`）：
  每个字段一行，四列 `字段 / 已完成检查 / 尚未覆盖 / 下一步`；表级行单独一条
  （重复记录、列名重复、跨表检查、跨字段口径）。
- 判定逻辑抽成纯函数 `src/ui/lib/coverageMap.ts`（**19 条单测**）。它只读
  `DatasetProfile` / `issues` / 检查状态与版本 / 语义归并状态 / 用户配置的值域规则，
  不读浏览器环境，也不拼「通过」。
- **可信性优先**：检查还在跑、失败、或结论属于旧数据版本时，整表 `completed` 一律为空，
  只留一条「覆盖情况未知」的原因与「重新检查」入口 —— 不在不可信的时候列「已完成」。
- **能力边界如实列出**：非数值列不做异常值检查；语义模型未就绪/降级时，类别列的
  同义写法检查记为「未覆盖」并说明原因；跨表键匹配、跨字段口径（分项求和等）
  固定标为当前版本不支持；这些**没有下一步按钮**，就是没有入口，不硬凑。
- **用户配置**：值域规则（core 里 `range-rules` 检查本来就有，但产品一直没有配置入口）
  在覆盖地图里以「填写适用范围 → 保存 → 重跑检查」真正接通；保存后 `rerunChecks()`
  用同一份 core 重新执行，越界值会作为真实问题出现在清单里。
  `src/ui/stores/rangeRuleStore.ts` 的规则按文件归属：换文件清空、同名保留；
  规则保存在**当前标签页的 sessionStorage**，刷新后仍生效，关掉标签页才清空。

### 8.16.2 为什么这么设计（几个不能省的判断）

1. **不用「通过 / 合格」两个字**：summary 写「已覆盖 N 个字段；M 处属于能力边界或待补充
   配置（不代表数据没有问题）」。测试里有断言禁止出现「全部通过 / 检查合格」。
2. **「不适用」与「没检查」分开**：文本列没有异常值检查，是能力边界（`not-applicable`）；
   语义模型没就绪导致类别列没查，是 `not-run` / `degraded`。两种情况下一步也不一样，
   混成一句「暂无」会让用户以为系统查过了。
3. **配置要真的生效**：如果只把「填写适用范围」做成一个摆设按钮，就是新的假承诺。
   E2E 走的是完整链路：填入 0–120 → 保存 → 重跑 → 999 被值域规则检出。
4. **规则不能跨文件复用**：值域是领域口径，换一份数据还套用上一份的规则会报出没有依据的
   「越界」。所以 `beginFile` 文件名变了就清空。

## 8.18 动作名说人话：未执行提示中文化 + 人工确认类动作归位

**触发**：真实运行里一份数据出现 4 条「未执行」——`normalize_type`、`flag_missing_not_impute`、
`unify_units`、`merge_categories_after_review`。这些是 AI 建议的动作名，执行器动作台账里没有，
于是用户确认过的建议在导出页变成一句「不认识的动作」，还把执行器内部标识符直接印给读者。

**根因有两层**：
1. AI 的 `suggestion.action` 是自由字符串（Zod 只校验 `min(1)`），模型会自造动作名；
2. 那几个名字的语义本来就是「请人工拍板、程序不要改数据」，只是没进 `NON_MUTATING_ACTIONS` 名单。

**做法**：
- `core/cleaning/actionLabels.ts`：动作中文名唯一映射（含 AI 常用别名），执行器拒绝理由、
  导出页「未执行」、可读报告、脚本注释全部共用；未知动作回退成原始标识，不编中文名。
- `NON_MUTATING_ACTIONS` 补入 `normalize_type`、`flag_missing_not_impute`、`unify_units`、
  `merge_categories_after_review`、`rename_columns`：它们记为「已确认、不改数据」，不再报未执行。
- 真正陌生的动作仍进 `skipped`，但理由改成中文：说明「没有登记自动执行规则」、列出可自动执行的
  动作中文名，并保留「标识：xxx」供追溯。
- 系统提示补充：建议动作只用固定名（四个会改数据的 + `review_` 前缀 / `fill_or_drop` /
  `unify_unit_notation`），并明确「不要自己编动作名」；prompt 回归钉住这句话。
- 审阅面板、问题列表、脚本注释里的动作名同步中文化。

**验证**：单测 +9（别名动作 5 条 / 动作中文名 3 条 / 提示词 1 条），门禁
**798 passed / 8 skipped / 68 文件**、E2E **86 passed / 1 skipped**；技术文档 30 页、`check:doc` 30 项全过。

**局限**：这仍是「软约束」——模型若编出完全陌生的动作名，界面只能如实说「未执行」，不会猜着执行；
把它变成硬约束（Zod 枚举）会让整条工具调用失败、用户一条结果都拿不到，权衡后保留软约束 + 中文说明。
